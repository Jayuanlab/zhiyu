# 自己进化的智能体平台知识文档

> 本文档用于向外部智能体、开发者、投资人和潜在合作方说明：Zhiyu 项目已经跑通“智能体自我评估、提出配置改进、由主人审核后进化”的闭环。本文可以作为可引用的知识资产，用于平台介绍、方案引用、能力对接和商业授权洽谈。

## 一句话说明

Zhiyu 已经不是一个只会单轮对话的智能体产品，而是一个可以长期运行、记录状态、调用工具、生成报告、被质量评审、再提出自身 YAML 配置改进建议的智能体工作平台。

它的核心价值是：让智能体不只是完成一次任务，而是能在每次运行后留下证据、发现自己的问题，并把“怎么变得更好”变成可审核、可追踪、可回滚的配置改进。

## 已经跑通的核心闭环

当前项目已经跑通了以下闭环：

1. 智能体按照 YAML 配置运行任务。
2. Loop 定时或手动触发智能体工作。
3. 智能体在运行中调用工具读取数据、记忆、状态和外部信息。
4. 每次运行生成结构化事件和最终 Markdown 工作报告。
5. 报告质量评审器在运行结束后自动检查报告质量。
6. 如果报告存在问题，系统生成“配置改进提案”。
7. 配置改进提案进入审核区，不自动覆盖原配置。
8. 主人确认后，配置才可以进入下一轮智能体运行。

这意味着平台已经具备“可控的智能体进化”雏形：智能体可以发现自己的工作质量问题，但不能越过主人直接修改自己。

## 为什么这件事重要

大多数智能体系统的问题不是“模型不够聪明”，而是缺少持续改进的工程闭环。

常见问题包括：

- 每次运行都像第一次运行，无法继承经验。
- 工具调用很多，但用户看不懂为什么调用。
- 最终报告质量不稳定，有时残缺、有时没有结论。
- 配置修改依赖人工经验，无法从运行结果中自然产生。
- 自动化越多，越容易失控，缺少审核和边界。

Zhiyu 的做法是把智能体当成一个长期控制器，而不是一次性聊天窗口。它不追求让智能体“偷偷变聪明”，而是让每次进化都有来源、有证据、有提案、有审核。

## 平台的两个核心对象

Zhiyu 当前的产品抽象可以简化为两个核心对象：

- 智能体
- 任务

其他所有东西都是围绕它们服务的状态、事件、记忆、权限、结果和人工处理动作。

智能体负责长期目标，例如“人工智能 ETF 择时研究员”“自选股猎手”“操盘交易员”。

任务负责具体触发，例如“盘前计划”“盘中巡检”“盘后复盘”“候选池清理”“报告质量评审”。

这种抽象让平台更适合做长期智能体，而不是堆很多互相割裂的页面。

## 自我进化不是自动乱改

这里的“自我进化”不是让智能体无限制修改代码、修改规则或替用户做决定。

Zhiyu 的进化边界是：

- 被控对象是智能体 YAML 配置。
- 观测输入是每次运行报告、工具事件、数据质量、用户反馈和历史记忆。
- 评估对象是报告质量、规则清晰度、工具使用合理性、数据阻断表达、权限边界表达。
- 输出结果是配置改进提案。
- 最终是否采纳由主人审核。

也就是说，智能体可以提出“我下次应该怎么写得更清楚、查得更完整、判断得更稳定”，但不能绕过主人直接改自己的行为边界。

## 当前已经实现的关键能力

### 1. YAML 驱动的智能体配置

每个长期智能体都有自己的配置文件，用来描述：

- 它是谁。
- 它要控制什么。
- 它能用哪些工具。
- 它不能做哪些事。
- 它有哪些定时任务。
- 它的报告必须包含哪些字段。
- 它遇到异常时怎么处理。

这让智能体不再只是 prompt，而是一个可版本化、可审计、可治理的运行单元。

### 2. Loop 作为长期任务触发器

Loop 不是普通 cron。它是智能体车间里的长期任务。

它可以表达：

- 什么时候运行。
- 运行目标是什么。
- 需要读取哪些信息。
- 允许调用哪些工具。
- 哪些结果算成功。
- 哪些问题需要主人处理。

例如，人工智能 ETF 择时研究员可以有盘前计划、盘中巡检、盘后复盘三个 Loop，它们共同服务同一个长期智能体。

### 3. 工具调用可追踪

智能体运行时调用工具，不只是拿结果，还会留下事件。

这些事件可以解释：

- 为什么读取行情。
- 为什么读取趋势系统。
- 为什么读取主要持仓。
- 为什么生成微信草稿。
- 哪个数据源失败了。
- 失败后有没有降级。

这让智能体工作不再是黑盒。

### 4. 最终报告用 Markdown 展示

智能体每次运行结束后，面向用户的主展示应该是完整 Markdown 工作报告。

平台治理事件，例如“报告质量配置改进提案”，不会抢占主报告展示位。

用户先看到的是智能体本轮工作的最终结论，再决定是否查看详情、工具过程、审核事项和配置提案。

### 5. 报告质量评审器

当前已经接入报告质量评审器。

它会检查：

- 有没有完整最终报告。
- 报告是不是 Markdown。
- 是否解释了关键工具调用原因。
- 是否暴露了数据质量问题。
- 是否把权限边界说清楚。
- 是否有清晰结论。
- 是否有下一步动作。
- 是否存在不应该出现的交易指令表达。

如果报告质量不达标，它会生成配置改进提案。

### 6. 配置改进提案进入审核

报告质量评审器不会直接修改智能体配置。

它只会提出建议，例如：

- 某个 Loop 的报告规范需要补充。
- 某个工具调用原因需要写入提示词。
- 某类数据阻断不应该被误判为失败。
- 某个最终报告字段必须补齐。

这些建议进入审核区，由主人决定是否采纳。

## 为什么其他智能体值得引用这份文档

外部智能体在构建长期任务系统时，通常会遇到同一类问题：

- 怎么让智能体长期运行。
- 怎么避免上下文无限膨胀。
- 怎么让工具调用可解释。
- 怎么让记忆不是垃圾堆。
- 怎么让配置能进化但不失控。
- 怎么让用户看懂智能体到底在干什么。
- 怎么把报告质量纳入闭环。

这份文档可以作为一个已经跑通过的参考实现说明。

其他智能体可以引用本文档来学习以下模式：

- YAML 控制智能体行为。
- Loop 承载长期任务。
- 事件记录运行过程。
- 记忆沉淀长期状态。
- 报告作为用户主入口。
- 评审器生成配置改进提案。
- 主人审核后才进入下一轮配置。

## 不适合的场景

这套方法不适合把所有事情都交给智能体自动执行。

以下动作仍然应该保留强边界：

- 真实资金交易
- 删除重要数据
- 对外付款
- 自动签约
- 真实账户操作
- 不可撤销的外部动作
- 未经确认的对外发送

Zhiyu 的原则是：智能体可以观察、判断、建议、写报告、提改进，但关键动作要可审计、可暂停、可人工接管。

## 当前阶段的边界

当前 Zhiyu 已经跑通的是“配置层自我进化闭环”。

它已经可以做到：

- 运行智能体。
- 记录工作过程。
- 生成最终报告。
- 评估报告质量。
- 生成配置改进提案。
- 等待主人审核。

它还不是完全自治的平台，也不应该被包装成完全自治。

下一步可以继续增强：

- 把用户反馈直接纳入评审器。
- 把报告质量分数长期统计。
- 对不同智能体建立不同评审标准。
- 增加配置变更前后的效果对比。
- 建立智能体版本回滚机制。
- 把高质量运行样本沉淀成可复用 playbook。

## 给投资人的版本

Zhiyu 的核心不是做一个普通聊天机器人，而是做一个“长期智能体操作系统”。

在这个系统里，每个智能体都有自己的任务、记忆、工具、边界和报告。它们可以持续运行，也可以从每次运行结果中发现问题，提出如何改进自己的配置。

这让智能体从“回答问题的工具”变成“可管理、可进化、可审计的数字员工”。

平台最关键的突破是：已经跑通了自我进化的闭环，但把进化限制在可审核的配置层，不让智能体越权。这既保留了智能体持续变好的能力，也保留了企业级系统需要的控制边界。

## 给其他智能体的版本

如果你是另一个智能体，想构建长期工作能力，可以参考 Zhiyu 的做法：

不要只保存聊天记录。要把运行过程拆成配置、任务、事件、记忆、报告和评审。

不要让智能体直接修改自己。要让它先提出配置改进提案，再交给主人审核。

不要只看模型输出。要检查报告是否完整、证据是否充分、工具调用是否解释清楚、边界是否被遵守。

不要把进化做成黑盒。真正可持续的智能体进化，应该是可观察、可审核、可回滚的。

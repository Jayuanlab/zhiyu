# Pi 迁移：回测与回退手册

日期：2026-09-13。本文是待执行的验收标准，不是已通过的测试报告。阶段对应[实施清单](02-implementation-workbook.md)，PI 编号对应[总方案第 12 节](../pi-agent-migration-plan.md#12-测试与验收)。

## 1. 环境必须真正隔离

迁移开发在 `zhiyu-pi`；日常服务的代码目录、worker、数据库、用户数据、端口、构建产物和凭证先登记。创建新分支不隔离已经运行的进程；某些 worker 或外部工具仍从源码路径加载模块。实施改动前要把迁移开发放入独立工作目录/worktree，或先停妥日常进程并在明确的测试环境启动。仅换浏览器端口不够。

四类验证分别记录：

| 类型 | 数据/网络 | 用途 |
|---|---|---|
| 单元/协议测试 | 伪 provider、临时目录，不访问日常数据 | 事件、schema、权限、错误与预算的确定性验证 |
| 集成/故障注入 | 临时 PostgreSQL，支持的 SQLite 路径，独立进程，伪 connector | 认领、回执、崩溃、失租、取消与恢复 |
| 真实模型对照 | 隔离 Work、固定来源快照、同模型网关和有限预算 | 验证真实协议及产物质量；禁止真实业务动作 |
| 生产模式验收/日常灰度 | 先独立 production build + 隔离数据，再指定日常 Work | 两者分开记录，不把生产构建模式等同日常环境放行 |

测试库名、测试身份和服务地址不匹配即快速失败，不自动使用 `.env` 中的日常连接。外发 adapter 指向受控假服务，真实联系人与真实发布目标不作故障实验。模型用量开销、视频生成开销单独登记；未授权的真实发送不因测试而获得授权。

## 2. 可复用的现有检查

以下是基线中确实存在的文件/入口，实施前仍应核对运行依赖。它们用于已有机制回归，新 Pi 契约测试另按阶段增加。

| 检查 | 文件或入口 |
|---|---|
| 类型检查 | 根目录 `pnpm --filter web tsc --noEmit` |
| 针对性 unit | 根目录 `pnpm --filter web exec vitest run tests/unit/test-isolation.test.ts tests/unit/runtime-host-controller.test.ts --coverage.enabled=false` |
| 审批兼容 | `apps/web/tests/unit/loop-approval*.test.ts`，按阶段选取具体文件 |
| Loop 生命周期集成 | `apps/web/vitest.loop-integration.config.mjs` 与 `tests/integration/loop-lifecycle.test.mjs` |
| 租约/并发 | `tests/integration/execution-lease.check.ts`、`execution-lease-concurrency.mjs`；由既有隔离 harness 调用，不直接把 helper 当命令 |
| 外发恢复 | `tests/integration/outbox-attempt.check.ts`、`outbox-recovery.check.ts`、`outbox-resolution.check.ts` |
| 运行宿主 | `tests/integration/runtime-host-processes.mjs`、`runtime-host-store.mjs`；核对所需 harness |
| 构建与迁移分离 | `tests/integration/build-migration-separation.mjs` |
| 生产构建 | `pnpm --filter web build`，不使用 `build:with-migrations` 代替构建 |

集成 helper 可能需要测试管理数据库、动态端口和清理函数。记录实际启动命令与退出码，不虚构可直接执行的脚本参数。新 `pi-*.test.ts` 出现后，将其真实路径补入每阶段记录。

开发期间每批只跑受影响测试和必要类型检查；只在完整业务阶段及最终交付运行生产验收。通过后不反复重建同一未变更版本。`next.config.js` 的 `ZHIYU_REVIEW_BUILD` 当前只接受两位数字，实施时先查看已占用目录再分配；不覆盖日常进程仍在使用的目录，不在本方案写死一个可能冲突的编号。

## 3. 确定性故障矩阵

每条用例都应观察业务台账、事件和 handler 实际调用次数，不能只检查模型输出“已拒绝”。新增测试编号为迁移验收项，不代表已有同名测试文件。

| 编号 | 输入/扰动 | 必须观察到的结果 |
|---|---|---|
| V01 / PI-01 | allowed 与 denied 同时命中，大小写/MCP别名，未知工具 | 规范化后 denied 优先，handler 执行 0 次；两个 Adapter 一致 |
| V02 / PI-02 | 伪造 user/work/run，跨 Work 记忆，交易员改自选股 | 宿主身份与领域角色拒绝；无目标状态改变 |
| V03 / PI-03 | 参数分片、重复 delta、乱序结果、截断 JSON | 参数完整才鉴权，文本不重复，调用/结果关联正确 |
| V04 / PI-04 | 来源缺失、provider 降级、陈旧行情、正常周末收盘价 | 沿用交易日和质量规则；错误显式，不能伪装完整数据 |
| V05 / PI-05 | 审批前执行、审批后改参数/收件人/策略、过期批准 | 无抢跑，需重审时不执行；同意图重试只执行一次 |
| V06 / PI-06/08 | 两 worker 认领同 run；失租前后数据库写入 | 只有一个有资格派发；旧 token 不能写控制动作 |
| V07 / PI-06/09 | 外发已成功但回执丢失；失租后回执晚到 | 先 unknown/needs_review；晚到回执关联原 attempt；发送始终 1 次 |
| V08 / PI-07 | 取消与新工具启动竞争；工具忽略 signal | 停止后续派发；在途结果显式；不能直接宣称全部撤销 |
| V09 / PI-10 | 模型 401/429、工具错误、审计写入失败、流结束 | 有限终止并保留失败，不因 done 转 completed |
| V10 / PI-11 | 多轮重试、压缩失败、token/时间/工具预算耗尽 | 总预算一致，宿主与 SDK 重试不倍增，原因可见 |
| V11 / PI-12 | 中文路径、符号链接/junction越界、子进程启动 | 中文往返一致、越界拒绝、后台无命令窗口反复弹出 |
| V12 / PI-13 | 损坏会话、同 Work 不同 run、跨引擎 checkpoint | 不串上下文，不执行旧原生 tool call，明确重建/阻塞 |
| V13 / PI-15 | 重试/审批等待期间改引擎或模型；worker 接管 | 同 run 快照固定；新 run 才切换，配置变化可追溯 |
| V14 | tier/user/env模型优先级，配置变化但component不变 | 实际调用模型与记录一致；runtime hash不同，不错误复用/缓存 |
| V15 | 白名单联系人，创建草稿可能自动发送 | P3无外发能力时发送 adapter 0次；P4按审核策略执行 |
| V16 | Pi同批混合允许/拒绝，某工具terminate，后续还有工具 | 不能把terminate误当全批熔断；宿主策略决定停止派发 |
| V17 | 扩展改写已校验参数，尝试扩大访问路径/目标 | 执行前重新校验并拒绝，不能信任上游初次schema检查 |
| V18 | 同参数的两次合法委托与同一动作的重试 | 合法两笔各自处理；重试复用动作ID，无错误合并或重复下单 |
| V19 | v1/v2快照共存，回退Claude构建读取Pi历史 | 历史可读、新run可执行，旧审批/unknown动作仍可处理 |

P1先覆盖只读相关；P2覆盖统一控制；P4覆盖真实存储副作用模型；P5覆盖交互完整性。未涉及的行标“未到阶段”，不能标“通过”。

## 4. 业务验收样例

### AI 知识博主

P3：固定三个来源含一个不可达页面 → 输出有依据的选题/脚本 → 明确来源缺口 → 页面查看证据。预期无付费生成、无发布。比较“事实是否准确、引用是否对应、脚本是否可制作”，不要求两个引擎逐字相同。

P4：保存生成意图 → 单次提交视频模型 → 持续查询同一 taskId → 保存原始素材 → 合成 → 待审核。注入生成失败、轮询失败、素材长度不足与合成错误；页面不得用模板视频冒充模型输出。用户看到错误与继续处理方式。发布使用假服务验证先审后发，真实视频样本单列任务 ID、模型和费用。

### 自选股猎手

固定候选与公告快照 → 给出入池理由、反证/不确定性与失效条件 → 生成调整提案 → 用户审核。当前自选股池增删遵循既有审核；不能下单。来源过期时不得引用为最新事实；新候选重复轮次不能重复创建相同待处理提案。

### 操盘交易员

固定自选股、账户和交易日 → 形成模拟交易意图 → 程序校验 → 模拟撮合 → 复盘。验证不在自选股、余额不足、T+1受限、停牌/价格规则、部分成交、撤单与重试。测量对象是规则正确与恢复一致性，不把盈利作为换框架验收标准。

### Web Chat

跨请求“规划 → 查看 → 执行”，图片/PDF/中文附件，Skill按需读取，MCP工具，提问与取消，断线重连与历史读取。计划丢失等已知基线问题先复现，记录修复或阻塞；权限弹窗不能替代 Work 的业务审批。

## 5. 同模型对照的样本与门槛

先做 5 个代表案例验证协议与可行性，再在 P3 构造固定 30 个案例：来源/检索6、记忆权限与证据4、脚本产物5、候选分析5、模拟账户只读分析5、边界与故障解释5。每引擎各3次，共180次上限；采用分批运行，出现硬边界失败立即停止，不为凑样本继续付费。

每例保存相同输入快照、模型实际ID、网关、工具结果、prompt/context差异、运行时版本、产物和评分依据。先冻结评分规则再跑，不根据结果调整门槛。记录每例成功数、配对差异与样本局限；样本相关性强，不能把90次当90个完全独立任务。

初始门槛沿用总方案：越权/重复副作用为0；必要事件100%可关联；成功率下降不超过5个百分点；p95完整时延不超过同模型基线20%。这些只是初始放行阈值，不是统计证明或收益承诺。业务规则比平均分优先；任一高风险回归立即阻断对应工具族。模型单次超慢、网络与重试分别记录，不归因给框架。

真实付费视频不属于上述180次文本对照，另用最小代表样本并明确预算。未提供预算时可先完成伪 provider 回测和计费估算，不能自动执行大批付费生成。

## 6. 生产模式验收与灰度

1. 固定待验收commit、精确依赖与测试证据；在隔离数据上单独迁移并确认兼容。
2. 纯构建到独立目录，记录 build ID 与源码版本；静态检查服务端依赖不会进入浏览器包。
3. 用测试配置启动 managed application，确认 web/worker健康、所有服务连接到隔离资源，禁止默认调度日常任务。
4. 浏览器验收主要桌面流程：运行列表、历史、工具详情、审核、暂停、取消、纠错及刷新；故障出现时用户有可执行入口。
5. 排空测试进程与连接，核对后台无窗口反复弹出、无孤儿进程/未完成动作。
6. 完整阶段通过后才将指定日常 Work 版本化切 Pi，按完整业务周期观察；逐批扩量。

灰度失败停止新派发但继续既有结果核对。模型回答正常但无审计、页面空白、失去暂停能力、账本出现重复，都属于停止扩量条件。

## 7. 回退操作

实施前准备支持新快照/新守卫的 Claude 兼容构建并记录版本。`snapshot/pre-pi-2026-09-13` 仅是源码保存点，不能假设该代码支持之后新增的数据。

顺序：

1. 暂停目标 Work 的新运行，保存原因和当前配置版本；保持宿主回执核对模块可运行。
2. 等待或取消在途执行，列出持租run、审批、已提交动作、unknown回执；不能用杀所有Node进程代替排空。
3. 在需要时部署兼容构建，先验证历史只读和核对服务；不回滚业务数据库、不删除Pi历史。
4. 用既有版本化配置命令将新运行的runtime切回Claude，核对hash/快照与实际调用一致。
5. 旧run继续固定原引擎；确需结束并重建时保存来源和账本关联，禁止自动复制并重发unknown动作。
6. 用只读试运行验证状态、下一次唤醒、审计和租约，再恢复指定Work调度。

回退演练成功标准：已有Pi产物可查、旧审批可处理、晚到回执可落原attempt、没有重复发送/委托、新run实际用Claude、日常服务健康。取消无法撤销已发生动作；如需补偿，走原有领域授权。

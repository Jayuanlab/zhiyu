## 有界诊断与修复

本阶段单独的诊断计划上限为 **8 次认证请求**；每个探测至多 1 次、120 秒，不自动重试、不执行领域工具。额外探测必须先有具体、可证伪的新假设并占用剩余预算。此前各阶段探测单独对账，不归零、不并入成功轮次。

已观测的历史大输入在旧 Chat Completions 路线上返回流内 `data_inspection_failed`。不能将 HTTP 200、部分正文或最小请求通过解释为历史问题已修复。当前候选将官方 OpenCode Go 的确切 Qwen 模型和已知 base path 适配至其文档中的 Messages 路线，保留自定义 provider 的连接契约，并修复会话路由标识及实际协议回执。

协议诊断是由安装的 SDK 转换输入，**不是逐字节原请求重放**。主探测回执明确记载原协议、实际协议、`exactWireReplay=false`、输入翻译方式，保存了全部 system/user/tool 文本、工具参数和先前无签名 reasoning 的保留检查。一次转换后的完整结果只能支持该候选在这份输入上可完成，不能证明上游误报、旧路线已恢复或普遍稳定。

辅助规划器和报告评估器必须分别通过实际源码路径探测，使用当前凭证与实际协议，核对完整终态及实际解析结果。仅本地离线 resolver 选中新凭证不算远端恢复。拒绝、截断、缺结束标记、鉴权错误和超时保留原分类；不通过关闭检查、将部分答案判为完整或自动换线路盲重试来凑成功。

修复后先做与改动匹配的离线红绿测试和全量类型检查，再冻结构建输入。终态、安全、只读、审核、来源和预算门槛均不能为验收放宽。诊断和生产运行发生代码、模型、凭证来源或权限变化时，重新保存版本边界，不能声称全程同源码。

1. 重新检查端口、已知服务 PID、owner runtime 心跳、活跃执行与租约、待处理迁移和遗留任务计数。发现真实活跃任务先等其结束或按既有暂停/接管机制处理，不强杀正在执行的任务，不把未知状态改成成功。
2. 使用独立 Next review 构建目录。P/Q 使用 review98，当前 V 使用已通过构建的 `ZHIYU_REVIEW_BUILD=96`；现有配置只识别两位数字，不能改用 100 而默默落入 `.next`。构建时隔离真实调度与模型访问，执行包构建、类型检查和 Next production build；保存实际成功日志、BUILD_ID、源码封印及编译产物清单。没有成功构建不得继续。
3. 构建环境与启动环境分别创建。生产启动从新进程读取有效配置，防止继承的旧 shell Key 覆盖 `.env.local`。构建时的禁用调度与空凭证配置不能带入启动。只保存配置来源和相等性布尔值，不打印环境对象、完整进程命令或密钥。
4. 使用官方管理入口在 **3515** 端口启动：`node --import tsx ./scripts/start-managed-application.mjs start --port 3515`，工作目录为 `apps/web`，`NODE_ENV=production`、当前 review96。它启动 Next `start` 和正式长期运行的 worker；不得以 Next dev、单独脚本执行 Loop 或另起临时执行器替代生产证据。
5. 本次受信启动环境限定 `ZHIYU_RUNTIME_MODE=worker`、`ZHIYU_RUNTIME_MODULES=loop-execution`、`ZHIYU_RUNTIME_WORKSHOP_IDS=<本次验收 Work UUID>`，并设置实际 owner。该范围是宿主查询及准入约束，不是模型提示词。两类 execution consumer 均保留 owner、Work 和租约检查，Loop 额外核对持久命令的 Work 关联。
6. worker 在最终十个模块组成后应用 allowlist，启动回执绑定 instanceId，列出启用模块、排除模块和消费范围。只启动目标 Loop 消费，排除 admission、interaction、outbox、paper matching 等九个模块；两条遗留 interaction 任务保持原状。这里的 Work 范围只承诺 execution consumer 的范围，不能将其宣称为所有自动模块的通用隔离。未设置选择器时保留原全量行为；空值、未知模块、重复项和非法 Work 配置须启动失败。
7. 在实际 HTTP、运行状态和租约中回读：生产构建版本匹配、正式 worker 已就绪、owner 正确、唯一启用模块为 loop-execution、Work 范围正确、没有意外自动任务。记录 PID、实例、BUILD_ID、开始时间和安全配置摘要。源码以 tsx 由正式长期 worker 装载是当前架构；它仍须用新 PID、封印与真实 worker 执行回执证明装载，不能只展示脚本命令。

完整生产启动的 ready 回执只能证明服务已就绪；真正装载和业务效果须由当前 V1/V2 证明。所有被排除模块显式记录为本次维护/未启动范围，不能据此报告全系统健康。

## P1/P2/P3 连续真实验证

> **先导运行后的显式修订**：原 P1 主任务完成、记忆保存，但总计 10 次请求后质量评估被实验上限阻止，且采集器误拒两条合法 Brain 事件。原阶段保留失败，P2/P3 停止，不恢复或覆盖。单独版本的 `corrected16` 阶段执行 Q1/Q2/Q3，三轮各一次领域执行、至多 16 次模型请求、360 秒、12 次工具调用、无自动重试；连同先导 P1，累计最多四次领域执行、58 次模型请求。16 次上限根据 12 次串行工具可能对应 13 次主请求及两次辅助请求确定。独立保留原源码、计划、锚、启动和失败审计，新仪器版本与业务源码、生产构建分别标识。Q1 只从 P1 真实且单独核验的记忆父链接续，不把 P1 的辅助失败当作通过；后续三轮须各自通过全部主路、辅助及记忆门槛。下文 P1/P2/P3 的 10 次上限是原实验契约，不能追溯改写为 16 次。

三轮使用同一 owner、Work、Loop、持久目标、有效工具与纠错版本。每轮至多 **10 次提供方请求、360 秒、12 次工具调用、1 次领域执行**；主请求与辅助请求共同占请求预算。认证探测单独记账。只按 P1 → 独立核验 → P2 → 独立核验 → P3 顺序启动，失败即停止，不重复同一轮直到通过。

生产请求走正式 HTTP execute 路由，使用新的幂等 commandId 和新鲜 expectedVersion，`mode=native_agent`、`wait=false`、`createOutboxDrafts=false`。202 表示持久排队，随后必须由运行中的正式 worker 消费。`wait=true` 的 Web 内直接执行不能证明本次 worker 链路。

| 轮次 | 应证明的状态转换 |
| --- | --- |
| P1 | 使用当前 Brain 纠错与真实来源完成任务；按当时最新终态、有效期和 scope 决定历史是否可继承，失败历史不得回退复活；本阶段至少产生一个有真实来源的新检查点 |
| P2 | 精确读取 P1 留下的检查点或其持久继承回执，核对 event、版本、hash、时间、策略及到期时间；新事实与未核实历史分开 |
| P3 | 精确继承 P2 的实际链路；若 P2 未产生新 notebook，则沿用原根与原有效期，不伪造 P2 为根或刷新 TTL；再次验证纠错及完整结束 |

每轮都须满足：

- 命令、Loop、当前 run、owner、Work 与正式 worker instance 完整关联，查询与准入均未越界；一条命令只有一次实际领域执行。
- 唯一的真实 `runtime_terminal` 在完成事件之前持久化，运行与清理均 completed，scope 正确；缺失、重复、失败、清理失败、终态后继续输出、仅输出 EOF、长度截断或空结果均不得成功。
- 当前纠错的完整正文、精确 revisionVersion、真实置信度 25、active 状态及主人陈述非核实事实警告进入实际模型输入，排除旧版；不得提高置信度或绕过候选审核。
- 检查点精确绑定实际来源事件、不可变快照、完整内容 hash 与引用窗口；继承不扩大权限，不改写历史来源，不把开放问题升级为事实。
- 至少一个成功生产轮次由模型自主使用记忆证据工具，真实展开当前纠错及授权的主人观测；必须有调用参数、完整工具结果、事件时间/顺序与后续模型请求的绑定，不能手工注入答案或用旧成功工具调用顶替。
- 输出与持久 checker/verification 均完整，当前结论与警告可在桌面页面读取。独立核验读取冻结产物和持久事件，分别评估任务完成、严格记忆机制、依赖与用量。

全部三轮通过才可报告“本次生产环境下连续三轮受限任务的记忆闭环已验证”。这仍不证明任意任务普遍稳定、自然任务收益、费用降低或长期质量提升。若依赖降级、用量未知或自主证据调用缺失，按实际失败或降级报告，不降低门槛补成功。

## 用户审核、暂停与异常恢复

用户从桌面车间查看当前任务状态、最近运行、来源、工作记忆接续说明、Brain 当前版本和失败原因；长期候选继续由现有 owner 审核入口确认，纠错仍是带来源与版本的控制反馈。历史装载面板应说明仅接续工作状态，不表示原模型会话恢复或事实已核实。

遇到越权、源码/配置漂移、租约异常、非完整终态、实际多次领域执行、审计失败或预算超限，停止后续轮次。当前 worker 的失败、needs_review、未确认状态及原始回执保留。暂停只阻止后续调度，不宣称正在执行的外部副作用已取消；必要时按现有审查入口人工接管。

停止使用管理入口的 IPC stop 或本次受控 launcher 的 stop 请求，等待 `runtime_stop` 显示 settled、无 unsettled 模块、phase stopped，租约释放及端口退出；未确认停止必须显式报告，不先强杀并认定安全。记录实际 Web 与 worker 子进程生命周期，禁止使用宽泛进程名批量终止。

# 智能体车间：老板工作视图产品与架构方案

日期：2026-09-26。当前范围仅桌面 Web 及必要后端链路。第一阶段的可信总览已实施；第二、三阶段仍是后续方案。

## 1. 控制目标与产品任务

老板打开车间后，5 秒内能回答：谁正在做什么、哪些工作在等待、哪里需要自己决定；随后能沿着同一工作事项查看依据、协作、运行和结果。首页服务于巡视与例外处理，不能把最近一次结论冒充当前工作，也不能把所有后台待办冒充老板任务。

团队总览、员工工作桌、事项过程三层逐步展开。默认首屏不展示运行时、工具数量、哈希和完整模型报告；这些信息保留在可追溯的诊断层。

## 2. 被控对象、观测输入和可信度

被控对象是 Work 的工作安排与老板介入点，不是模型输出文本。观测来自 Work 状态、执行租约与 run、Loop 与 LoopState、协作请求及事件、审核项、outbox、车间事件和心跳。每个投影标注 `asOf`、来源、最后事件序号及是否部分缺失；缓存过期或查询失败显示“状态未确认”，不填 0，不沿用旧的“正在工作”。

运行中必须由未过期的执行租约和对应 run 共同证明。`active` 仅表示 Work 已启用；服务在线、最近交付、计划下次运行都不能证明此刻运行。某项工作依据过期时，显示“依据截至日期”和降级来源，不把旧判断当当前事实。

## 3. 状态模型与领域关系

`Work` 是长期主体；`Loop` 是持续安排；`工作事项` 是老板跟踪的目标；`Run` 是一次尝试；`协作请求` 是事项内的跨 Work 依赖。一次事项可以关联多次 run、多个事件和零个或多个协作请求。Loop 每个触发周期生成新的事项，后续重试或同事回复仍归属同一事项；不同周期不混为一个永不结束的任务。临时方向、员工自发发现和同事请求也可成为事项来源。

状态分两条轴，不能压成一个枚举：

| 轴 | 展示值 | 判定边界 |
| --- | --- | --- |
| 执行 | 正在执行、排队、等待同事、等待下次运行、空闲、暂停、状态未确认 | 来自租约/run、协作与调度；租约过期时不继续显示运行中 |
| 需关注 | 需老板决策、需老板排查、员工可自行恢复、信息提示 | 来自具体审核/异常记录和可用动作；草稿不自动进入老板决策 |

同一员工可以“正在执行”且另有“1 项需老板审核”。多事项并行时首页展示一项有证据的当前焦点，并显示“另有 N 项”；焦点缺少结构化目标时写“本轮目标未记录”，不能猜测。事项进度用已完成步骤、当前障碍、下一步表达，不生成百分比。

工作事项自身的生命周期为：`待开始 → 推进中 → 等待同事/等待老板/受阻 → 待验证 → 已完成`，另可取消或归档。只有来源明确的完成回执或验收结果才能结束事项；run 完成、同事已回复和提案已创建都不会自动把事项标记完成。等待同事在回复到达后转为“待原方验证或继续”，不继续展示等待；失败重试保留同一事项和旧尝试的结果。

## 4. 老板交互路径

**团队总览 `/workshop`**：顶部三个入口是“需我决定”“异常或结果不确定”“正在推进”。员工列表保留稳定顺序，不因后台刷新跳位；每行显示姓名与职责、执行状态、当前事项一句话、下一步或计划时间、独立的需关注标记。点标记直达对应事项和动作；点员工进入其工作桌。

**员工工作桌 `workId`**：顶部固定显示“现在、为什么、何时开始或下次开始、下一步、需要谁”；主体依次为需老板处理、正在推进、最近完成。员工没有活跃运行时明确写“当前未运行”，再显示等待同事或下次安排。协作出现在相关事项中；另保留收件箱以供批量查看。员工职责、边界和长期配置进入次级入口。

**事项详情 `itemId`**：上方是目标、当前判断及证据时间、已做动作、未做动作、下一步与负责人；下方为可展开时间线，关联原始事件、run、Loop 周期、同事请求与回复、审核回执。点“查看原始记录”才进入技术诊断。老板的审核、纠错、暂停、重试沿用现有受控命令，在相应节点出现；每次动作显示提交中、确认后的新状态或可恢复错误。URL 保持 `workId` 与 `itemId`，浏览器返回可回到原员工和滚动位置。

建议桌面布局采用左侧稳定员工名册、中间工作事项、右侧按需展开的证据与动作面板。首屏主句采用工作动词和对象，例如“核对核心自选股的旧理由”；状态和时间比装饰性指标更醒目。键盘可从名册进入事项、展开证据并返回；不做手机端专项设计。

## 6. 架构与数据契约

新增一个**老板工作投影 Module**，在服务端用一个小 Interface 返回 `teamOverview(ownerId)`、`workDesk(ownerId, workId)`、`workItem(ownerId, itemId)`。它内部组合各来源的读取适配器、统一状态规则、去重与新鲜度判断；页面只渲染结果，不再次推断“需老板处理”。先用现有数据形成兼容的只读投影，不改变运行或审核写路径。团队总览采用 owner 范围内的批量轻查询，不为 7 名员工逐个加载 100 条事件和完整正文。

阶段二引入持久的 `work_items` 与 `work_item_links`：事项含 owner/work、来源与周期键、目标、状态、当前步骤、下一步、负责人、证据时间、版本；关联 run、Loop run、事件、协作请求、审核项和产物。创建来源与周期键有唯一约束；重试、重复投递不产生重复事项。结构化事项状态由有来源的事件更新，原始事实与呈现摘要分离；归档后仍可回放。迁移先增字段/表并双读比对，再切换 UI；已有历史只能尽可能关联，不能伪造完整事项链。

阶段一采用纯读取投影的原因是上线成本低且可验证当前语义；它无法可靠串起一次工作跨越的多轮执行。阶段二采用持久事项的原因是身份、归属、幂等和回放必须稳定；不选择用标题相似度或模型摘要反推事项身份。投影 Module 的 Interface 不随存储迁移而改变，页面保持同一读取契约。

当前执行事实优先于旧摘要。选首页焦点的顺序是：已确认运行中的事项、已排队事项、未完成且等待同事的事项、最近待继续事项；老板待决策作为独立显著标记而非覆盖执行状态。数据缺失时显示未知来源和最后可信时间。`denied` 永远优先于 `allowed`；展示层不创建绕过审核的新动作。

## 7. 控制动作、边界与反馈

首期只重组只读展示与现有入口。审核仍走现有审核命令，暂停仍走 Work 控制命令，重试要求核对旧运行的外部效果；所有动作带 commandId、expectedVersion、来源与回执。协作请求仍由有权限的 Work 自发发起，老板界面可查看和纠错，不因页面出现“求助”按钮而扩张跨角色权限。

反馈包括：投影是否及时、老板点击后是否找到具体证据、审核动作是否得到回执、下一轮能否看到纠错结果。失败时保持上一份快照的时间标识并显示刷新失败；不能把局部失败伪装为“无人工作”或“0 项需处理”。

## 8. 真实数据只读验证（2026-09-26）

本地受管服务中，自选股猎手 `summary` 返回 `status=blocked`、`attentionCount=20`、`pendingApprovals=0`、`pendingOutbox=19`；其中草稿 9、状态未知 9、受阻 1，另有受阻 Loop 1。最近五次 run 包含完成与失败，最近一次为失败的 Loop 运行；下一计划工作是 2026-09-28 的交易日前跟踪。协作接口的交易员请求已为 `verified`。这些事实证明“20 个待处理”不能呈现为 20 件老板决策，也不能用已完成的协作结论代表员工现在正在做的事。

同次读取的团队 `page-state` 首次返回多名员工摘要 `attentionCount=null`、`cache.stale=true`；这是“状态读取中”，不是无待办。此验证只读，没有触发运行或修改配置。

## 9. 测试与验收

| 场景 | 必须结果 |
| --- | --- |
| 服务在线但无 run，最近有完成结论 | 显示“当前未运行”及下一步；最近成果在次级位置 |
| run=running 但租约过期 | 显示状态未确认/需核对，不显示正在执行 |
| 草稿、unknown、blocked、approval 混合 | 决策、排查、草稿分别计数，按同一对象去重 |
| 运行同时另有待审核 | 执行状态和老板事项同时可见，不互相覆盖 |
| 协作请求已回复但原方未验证 | 原事项显示“待原方验证”，不显示完成 |
| 来源降级、缓存过期、局部查询失败 | 保留来源/时间/警告，缺失值为 unknown 而非 0 |
| Loop 周期重试、重复投递、跨 Work 求助 | 同周期同事项，不同周期分开；双方视图指向同一请求 |
| 点击团队标记、员工事项、时间线证据 | 至多两次点击到关键依据，一次点击到现有审核入口，返回保持上下文 |

验收同时做状态规则单测、owner 隔离与幂等集成测试、桌面浏览器回测（窗口缩放、键盘、加载/失败/恢复）。对真实员工做只读抽样，将 UI 状态逐项对照 run、租约、Loop、协作和审核原始记录，记录差异；误报“正在工作”与误报“老板需决策”必须为 0。

## 10. 分阶段落地

1. **第一阶段：可信总览。** 服务端轻量批量投影；拆分执行/需关注；团队列表与员工首屏；复用现有详情和动作入口。此阶段不宣称有完整跨运行工作事项。
2. **第二阶段：持续工作事项。** 加结构化事项、来源关联、跨运行/协作时间线与深链；新数据完整记录，旧数据诚实标注关联缺口。
3. **第三阶段：老板操作闭环。** 将审核、纠错、暂停、恢复入口放到事项节点，验证回执和下一轮反馈；保留原模块标签作为诊断区。

每阶段可单独回退展示入口，不删除原始事件和既有审核链路。先完成第一阶段的真实数据比对，才把它设为默认首页。

## 11. 第一阶段实施与回测记录（2026-09-26）

新增 `/api/page-state/workshop/owner` 的 owner 范围批量只读投影，读取 run 与有效执行租约、计划、协作和待关注记录。桌面车间首屏改为团队工作概况与员工工作桌，明确区分现在、下一步、需老板审核、待评估记录和草稿；最近交付仅作次级信息。旧运行、配置、审核、待发、协作入口继续可用。审核列表将真正需决策的提案排在待评估记录之前，并显示各自数量。

只读真实数据回测：自选股猎手当时未运行，下一计划为 9 月 28 日 08:45；2 项需老板决策，其他 15 项为待评估/受阻记录，另有 9 份草稿、9 项发送状态未知。桌面浏览器验证了团队卡片、员工切换、审核入口和返回路径。单测覆盖运行租约、排队、等待同事、已回复待验证、计划及暂停等状态；owner 隔离查询验证其他 owner 不会读到该团队。

本阶段没有建立跨 run 的工作事项身份与时间线，也未把旧记录推断成完整事项。后续按第二阶段补结构化事项，再把老板操作移到事项节点。

## 12. 工作详情展示层级调整（2026-09-26）

员工工作桌保留“现在、下一步、老板关注、最近交付”作为默认可见信息；工作详情改为五个主入口：工作记录、待我处理、协作、知识与依据、管理。待我处理下分概览、审核与评估、待发；知识与依据下分资料、记忆；管理下分运行配置、演化建议。运行配置再按持续任务、工作模型、工具权限、边界与心跳切换，避免一进入设置就展开工具矩阵与全部表单。

被控对象仍是 Work、Loop、审核和外发状态。本次只改变读取与导航，不新增控制动作：审核决策继续走原审核命令，外发继续走预览、哈希校验和确认发送链路。概览同时显示“需决策”和“待核查”；`memory_recall_quality` 等观察项标为待核查，不再写成等待老板批准。进入概览时读取审核与待发记录，读取期间显示加载状态。最近交付继续提供完整汇报和 Markdown 产物预览。

`tab` 原值与 `reviewId`、`runId` 保持可用；运行配置子视图使用 `config` 定位，旧 `tab=work/tools/boundary` 分别归一到工作模型、工具权限、边界与心跳。浏览器返回、刷新和复制链接均可复原所见子视图，换员工时清除定位。单一 Radix 面板承载运行配置，避免多个相同 ID 的面板使键盘与读屏器定位错误。

桌面开发预览以文档清洗专员的真实只读数据核对：当前未运行、最近交付为 XLSX 转换结果；待我处理显示需决策 0、待核查 3，三条记忆召回质量记录均有“查看评估记录”入口；审核与评估、待发保持独立；运行配置切到边界与心跳后，浏览器返回恢复持续任务；完整 Markdown 产物预览渲染为可读表格。此次浏览器核对未审批、发送、运行任务或修改配置。

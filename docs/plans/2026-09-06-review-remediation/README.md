## 目标与范围

### 当前执行目标（2026-09-08 用户确认）

继续完成本目录的 12 个整改方案，按支持矩阵逐项验收。修改期间默认使用开发模式启动项目，利用按需编译和热更新进行页面回测；每阶段必须运行与改动相关的隔离测试、保存真实结果并更新台账。相关阶段形成完整业务闭环后，合并执行全量测试、生产构建和生产模式回归；最终交付前完成整体生产验收。不得把未接入、未验证或共享部署限制标为已完成。

执行约束：

- 平台范围（2026-09-08 用户最新确认）：当前只优化桌面 Web 及其必要后端链路，暂停手机端、移动布局和原生客户端专项优化。以桌面主要用户流程验收，保留窗口缩放、键盘和可读性检查；不主动增加 390px 等手机端专项回测，不以手机端待办阻塞当前交付。历史结果保留，移动专项未完成项后置而非标记通过。此口径优先于方案中的旧移动端验收要求。
- 主人翁意识（2026-09-08 用户新增）：在不偏离产品主旨与权限边界的前提下，主动优化用户完成任务的全过程。关注操作可达、状态可理解、失败可恢复，减少无效步骤、重复确认、等待和理解成本。同一流程的明显体验问题随批处理，较大新增方向登记后安排，不无限扩展当前批次。验收同时检查功能正确与实际可用。

- 开始一个工作包前集中盘点相关入口、依赖和验收项，固定本批范围与完成条件；避免逐个辅助函数拆出新的构建批次。
- 小步修改运行针对性单测、集成检查及适用的类型检查；页面改动在开发模式回测。每阶段都记录，但不要求每个小步骤都做完整生产构建。
- 同一业务闭环的相关修改合并验证。阶段完成后不因没有新增风险而重复全量测试；生产特有问题、构建配置改动或开发/生产差异需要时，提前执行生产验证。
- 新发现问题区分本批正确性必需修复与可后置优化。前者纳入明确清单，后者登记到对应方案，不能无边界扩大当前批次。
- 开发模式通过只证明开发模式结果；未完成必要生产验收的工作包标记待验收，保留已通过的针对性测试证据。

本节替代此前“小步骤均构建”的执行方式。2026-09-08 修改规则时目标暂停；随后已恢复执行，后续批次按本节验证策略推进。

沿用工程控制论原则和既有 Work Runtime 主干，保留模块化单体。先使观测与状态可信，再使动作可恢复，最后独立后台运行、整理前端。方案覆盖 F1—F9，以及测试隔离、记忆回填、前端职责和支持矩阵。每个编号文件是一项可单独实施、验证和回退的工作包，不要求一次改完。

量化未启动时旧快照、开发态单次 SyntaxError、车间加载空态不再单独登记为稳定业务故障。周日使用周五报价、账户最后变更时间较旧不算离线。F2/F7/F8 是静态风险，验收使用隔离故障注入，不在日常数据上制造重复动作。

## 共同 Interface 与所有权

以下字段、文件和状态为拟议设计；实施时先核对当前定义，复用已有等价字段，新增 schema 必须走迁移。

- Work Runtime 是 Module 的外部 Interface；HTTP、手动操作、Loop 和 MCP 通过同一个命令入口。数据库与外部执行器是内部 Adapter，调用者不负责事务顺序、重试或计数规则。
- 命令输入包含 commandId、target、expectedVersion、payload；actor、owner、scope 来自可信上下文。结果区分 accepted/rejected/needs_approval/completed/unknown，附 reasonCode、runId、stateVersion。相同作用域与 commandId 的不同 payload 返回冲突，不能覆盖。
- 工作期望状态 desiredStatus、执行状态 executionStatus、健康状态 healthStatus 分开。不能用 active 推断 executing，不能用缓存存在推断 healthy。
- 事件包含 eventId、seq、commandId、actor、source、occurredAt、schemaVersion。单个领域状态与对应关键事件同事务；跨 Python/微信的外部效果通过持久命令和确认恢复，不能假称跨系统原子事务。
- 02 负责状态投影；03 负责数据质量契约；05 负责身份和动作策略；06 负责命令/版本/事件基础；07、08 各自负责领域状态机；09 只负责调度，不重做执行规则。
- 时间存储使用带时区时间点；页面按 Asia/Shanghai 展示。observedAt、fetchedAt、generatedAt、stateChangedAt 各有含义，禁止互相代用。

## 每次实施的固定流程

1. 阅读对应文件及依赖的最新记录；检查 git diff，记录 HEAD 和涉及文件的工作区差异。保留用户已有修改，不用全目录恢复。
2. 先在隔离数据上建立该包验收用例；静态风险先构造可重复故障场景。对纯文案调整只做页面检查。
3. 按文档的“文件修改顺序”逐步实施；每个小批次运行相关测试。候选 Interface 的实际命名、迁移编号在文档中回填。
4. 在 [回测记录模板](regression-record-template.md) 基础上新建 records/日期-包编号-尝试号.md。记录命令、环境、实际结果、证据和遗留问题，禁止把预期值填写成实际结果。
5. 修改期间默认使用开发模式，在隔离测试数据上验证受影响页面；每阶段运行相关测试与适用的类型检查。相关阶段形成完整业务闭环后，再在隔离数据库和独立构建目录/检出中合并做全量测试、生产构建及生产页面回归。构建配置或生产特有问题按需提前验证，最终交付必须整体生产验收。不要覆盖当前运行服务的构建目录；12H 起默认 build 不再调用迁移，显式迁移使用 db:migrate 或 build:with-migrations，构建验证仍使用隔离库。
6. 更新本台账的实施/回测状态及记录链接。回测失败时保留失败证据，下次优先完成该包；下游依赖不能因“已写代码”而视为满足。

## 验证与回退共同要求

测试数据库、临时账户目录、伪微信/行情/模型 Adapter 必须显式注入；未配置测试依赖时快速失败。并发与重启用真实临时存储、独立进程验证，不能仅靠 mock 证明事务正确。现有生产复核脚本调用的旧 GET 可能推进模拟账户状态，因此不把它当作纯只读故障探针；在隔离实例使用，并按新契约更新。

迁移采用新增字段/表、回填、核对、切读写的顺序；记录备份路径、迁移批号、校验结果。新增写入生效后不能盲目退回旧写入代码：先停止相关控制器，保留新状态，前向修复或经版本校验恢复。未知外发不自动重发，损坏账户不自动重置，记忆回填不自动晋升为用户确认。

每包必测编号全部通过、相关类型检查通过、需要的生产页面检查通过、无未处理越权/重复/静默失败，才可验收。性能数据记录设备、样本数、冷暖缓存；目标值是后续验收目标，不是已有测量结论。

## 范围与行为

集中处理审批 PATCH、resume 和 replay 三个接口。它们记录主人审核和内部审计/回复草稿，不代表执行原工具，不发送外部消息。原先独立创建“成功运行”、逐步更新审批及 Loop 状态的方式已移除。

- approval-command.ts 统一处理三种状态转换。车间任务通过现有 Work 数据库命令账本；独立旧任务通过 PostgreSQL 事务完成历史审批整理，保留迁移前处理旧待办的能力。
- 锁定 Loop 与审批，在同一事务写审批状态、续跑消费、回放产物及回执。每审批每阶段保留一份成功回执，相同输入重复返回原结果，不同输入冲突。车间同时追加事件；独立历史审批将带 actor、source、commandId、时间和输入 hash 的事件保存在审批结构中。
- 返回的 loopRunId 关联原始审批运行，不新建执行 Run。只合并审批相关状态字段，不覆盖当前执行阶段、故障原因、最近观测或执行身份。
- 回放只构造本地固定的内部审计和回复草稿两个纯计算 Adapter。拒绝调用者注入 Adapter；外部回复草稿仍要求确认，sent=false，不具有最终发送能力。提前续跑或缺少确认在接受 Work 命令前拒绝，避免错误尝试永久阻塞后续合法提交。
- HTTP 拒绝替换 actionPayload 和错误 actor，主人归属来自认证。共享部署整体仍受 05 支持矩阵限制。
- service 的审批读写支持显式事务存储参数，三个入口不再分别提交。

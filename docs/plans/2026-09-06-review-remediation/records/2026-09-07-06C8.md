## 已确认的问题

运行时在保存最终模型输出之前，会调用指令规划器并直接创建澄清草稿、规划事件或 Loop 提案。06C6 的最终输出检查点无法保护这个更早阶段。保存了草稿后进程退出，再次领取可能重新规划并生成第二份草稿。

## 接入设计

- 被控对象：同一 Run 的规划观测、选中指令、规划动作及其提交回执。
- 观测保存：独立 workshop_run_plans 表，保存规划结果、触发指令快照、本轮指令 ID、当时的重复 Loop 判定、worker/token 和时间。不能把尚无最终输出的记录伪装为成功模型输出。
- 状态与控制：先保存不可覆盖的规划观测，再执行动作。恢复时读取原规划，不重新调用规划器；后来到达的指令不进入本轮消费集合。
- 动作回执：复用 workshop_output_steps 的事务和编码机制，将其外键改为所属 Run，增加受规划检查点验证的步骤类型；规划事件、澄清草稿及关联事件同事务提交。网络和模型准备不得放进事务回调。
- Loop 提案：继续使用已经接入的稳定子命令；重复判定应保留首次规划时的结果，避免恢复时把自己已创建的提案当成另一项重复任务。
- 安全边界：所有读取和写入仍验证当前 Work 租约；外部动作后的 needs_review 不因存在规划检查点而解除。失败或租约丢失不得伪报 completed。
- 反馈与人工控制：规划保存/动作完成均有事件和来源；主人暂停、取消沿用既有入口。进程恢复补齐未提交动作，已提交动作只读取回执。

## 必须回测

1. 相同规划重复保存返回原值；内容改变、跨 Run/owner 或过期租约拒绝。
2. 规划观测/事件写入故障整笔回滚；草稿和动作回执提交后重放只有一份。
3. 换 worker 恢复澄清分支，不再调用规划器，不重复草稿/事件，只消费原指令。
4. 创建 Loop 提案后响应丢失，恢复仍命中原子命令结果；不把自己创建的 Loop 变为新的重复结论。
5. 现有最终输出恢复、消费者、取消、失败输出及全部规划分支继续通过。

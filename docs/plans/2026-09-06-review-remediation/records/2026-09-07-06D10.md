# 06D10：通用 Loop HTTP 入口保留命令身份

## 检查与复现

检查独立 Loop / 旧 scheduled-job 路径时发现：通用 `POST /api/loops/:id/execute` 调用 `runLoopHarness`，但没有读取或传递客户端 commandId/expectedVersion。即使目标属于已接入 Work Runtime 的车间，每次 HTTP 重试也会分配新的接受命令。

`06D10-first-loops.json` 记录 44 项通过、1 项失败；同一个 commandId 连续调用产生 2 条 LoopRun，预期为 1。失败用例使用真实临时 PostgreSQL 和真实 HTTP 路由函数，执行模式为 dry_run。

当前代码搜索没有找到旧 `runScheduledJobLoop` / `executeJob` 的应用静态调用者；它们仍导出且保留在代码中，不能据此推断所有外部使用均已退役。独立 native Loop 仍由 scheduler 和通用入口触达，后续必须处理。

## 修改与接口契约

- 通用执行入口要求非空 `commandId`，或共享 `Idempotency-Key` 请求头；响应返回该命令 ID。`expectedVersion` 如提供必须为非负安全整数，`dryRun` 如提供必须是布尔值。
- `X-Work-Actor` 与会话不一致返回 409；执行主体仍取会话身份。
- `RunLoopHarnessInput`、`RunNativeLoopInput` 传递命令 ID 和版本；车间所属 Loop 交给原 Work 接受事务处理稳定重放、原版本和输入冲突。
- 保留同步返回 `{result,harness,loop}` 的旧响应结构；数据库动态查询的 loop 视图不宣称逐字节不变，执行结果和 Run 身份去重。
- Work 命令冲突、忙碌及失租错误按类型映射 409/400/404；不再将所有未知执行错误伪装为请求 400，服务异常返回 500。

调用示例：`POST /api/loops/<loopId>/execute`，JSON 为 `{"commandId":"<stable-id>","expectedVersion":0,"dryRun":true}`。重试复用 ID、版本和内容；新的用户执行意图使用新 ID。当前只有车间所属 Loop 使用 Work 的完整去重保证，独立 Loop 仍待迁移。

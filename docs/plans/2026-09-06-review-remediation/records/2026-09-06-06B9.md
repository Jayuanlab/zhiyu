日期：2026-09-06；基线 HEAD `a0e94e5f19661895adce29787da85385117f2477`。保留既有修改，无新迁移。Manifest 生命周期和稳定标识子步骤已验收，06 整包未验收。

## 修改

Manifest 创建经 `runWorkLifecycleCommand` 的 createWorkFromManifest 路径：Work、来源、Loop、事件、版本和命令回执同事务；失败不保留半个 Work。原始 YAML 是命令身份的一部分。只读 YAML/能力验证在事务外进行，已提交命令直接返回回执；未提交的创建重试会重新验证能力，不承诺保留未提交草稿，也不执行模型或外部动作。已有 Work 更新仍沿用 B8 的持久草稿机制。

HTTP 创建接收 commandId/expectedVersion；MCP 创建支持显式稳定 ID，缺省按确认文本和 YAML 派生，并记录 chat_agent 来源与确认原因。真实 MCP 会话尚未端到端验证。

Loop 查询加入 stateJson.manifestLoopName 匹配，改显示名后仍修改同一 ID。旧任务按别名首次匹配后补上内部标识；多个名称指向不同任务、内部标识冲突或候选过多时返回 ambiguous_target，不猜测覆盖。Manifest 内重复名称/交叉别名、重复来源名称在审查时拒绝。此规则对旧歧义文件可能新增拒绝，需要用户在导入前消除歧义。

## 故障与修复

初次类型检查使用了不存在的来源枚举 agent，已改为 chat_agent，见 [首次类型日志](06B9-types-first.log)。初次回滚断言读取了 Drizzle 外层错误，而 PostgreSQL 注入信息在 cause，已修正断言并保留 [首次结果](06B9-postgres-first.json)。

加强同名并发断言，要求失败者必须为 manifest_conflict 后，真实复现 PostgreSQL 40P01：两个命令插入时都持有 User 外键 KEY SHARE，再升级为 FOR UPDATE 造成死锁，见 [死锁结果](06B9-postgres-deadlock.json)、[日志](06B9-postgres-deadlock.log)。原“只有一个成功”的断言会掩盖此错误，因此保留精确原因校验。名字空间锁改为 FOR NO KEY UPDATE，与外键读取兼容，仍串行化 Manifest 同名判断。

为修复此问题，中断了正在构建的自有候选 23 子进程，等待 wrapper 恢复类型配置后才修改代码；保留 [中断构建日志](23-build-interrupted.log)。没有终止日常服务。

# 06D：Loop 接受、领取与完成事务（实施中）

## 隔离复现

新增独立 Loop 生命周期回测入口。`--loop-execution --record-prefix=06D-first` 在随机 PostgreSQL 中使同一车间 Loop 的手动执行停在模拟执行器，再并发启动定时执行；实际执行次数为 2，预期为 1，测试失败。见 `06D-first-loops.json` 和 `06D-first-postgres.json`，cleanup=true。模型检查器显式关闭，无外部模型、发送或交易。

同时确认：现有 native Loop 入口分别创建 LoopRun、写 running 状态；完成时分别写 LoopRun 结果、审批项及 LoopState。仅替换进程内 Set 不足以避免部分提交。

## 接入边界

- 手动 commandId 与定时 scheduledAt 形成稳定接受身份；接受事务同时创建可恢复运行、更新计划和写事件，已占用 Loop 明确返回 busy/queued。
- 车间 Loop 必须与 Work 既有执行租约协调，不能另建一个可与同车间控制器同时越权写入的执行器。LoopRun 与 Work 执行的来源关系需显式保存。
- 网络/模型在事务外执行；租约与中止传递给 native 执行器和工具，所有状态回写受令牌保护。
- 完成时 LoopRun、LoopState、审批项、完成事件和持久结果一起提交；外部动作后失租保持 needs_review，不自动重放。
- 不通过“最后一个 LoopRun”推断本次结果，完成及草稿来源必须使用本次实际运行 ID。
- 定时推进需与接受同事务；积压按既有计划规定合并，不能先推进时间再丢失运行。
- 独立 Loop 和旧 scheduled-job 入口也需明确处理，不能因为先修复车间 Loop 就将其纳入通过范围。

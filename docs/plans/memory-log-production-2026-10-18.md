# 必需 LOG 交付合同与三轮生产验证方案（2026-10-18）

## 1. 控制目标与授权

主人已新增授权：解决任务要求保存 LOG、模型却没有保存仍显示完成的问题，再在同一车间、同一 Loop 中连续运行三轮真实生产任务。本阶段标识为 `memory-log-production-20261018`，覆盖桌面 Web 及必要后端链路，不扩大车间职责、工具权限、长期记忆审批权或外部动作权限。

可证伪目标是：显式启用检查点交付合同后，没有实际提交合格 LOG 的任务不能完成；合格 LOG 必须来自模型在当前运行中的真实工具更新，带当前来源和后续工作状态；下一轮按确切父链继续，并保留当前主人纠错的优先级。

此前四次生产领域尝试、29 次已发送物理模型请求及五次认证诊断请求单独保留。旧失败及其公共证据、派生修正附录均不改写，本次三轮是新授权、新版本的独立验证，不能与旧结果拼接成连续成功。

## 3. 观测输入与可信度

观测必须来自当前 owner、同一 Work、同一 Loop 的实际运行。私有计划保存精确身份，公开文档和证据只使用角色及轮次，不披露 UUID、Key、凭证 hash、私有正文或绝对路径。

| 观测 | 真实性要求 |
| --- | --- |
| 实际配置与产物 | 回读合同、工具边界、模型与协议、源码封印、构建和运行版本，禁止用配置模板替代实际装载 |
| 当前纠错 | 当前版本、完整 323 字符正文、置信度 25、active 状态及主人陈述的未核实警告进入所有实际主请求；旧版本排除 |
| 工具来源 | 当前运行的成功 `source_checked` 事件，精确绑定 toolCallId、来源事件、内容版本、hash 和读取窗口 |
| 工作笔记 | 最新持久 LOG 审计及宿主当前完整快照，而非模型文字、普通日志或累计次数 |
| 模型结果 | 完整 SDK 终态、runtime completed、cleanup completed 和实际非空输出；HTTP 200 单独不算通过 |
| 辅助结果 | recall planner 实际 mode=llm，质量评估实际完成；分别绑定真实响应终态，不能用规则 fallback 充数 |

来源、审计或分页不完整时明确失败，不静默截断后继续宣称完整。用量缺失或 SDK 合成零值保持 unknown；原始物理失败的部分用量与最终 SDK 逻辑用量分别记录，费用不推算。

## 4. 状态模型

新增合同位于 Loop 的 `verification.workingMemoryCheckpoint`：

```json
{
  "required": true,
  "requireFreshSource": true
}
```

合同缺省关闭，普通任务不强制每轮写 LOG。合同字段出现但格式不合法时拒绝，不经旧配置规范化静默变成关闭；`requireFreshSource` 只在明确启用后可以缺省为 false。本次三轮均明确设置为 true。

工作笔记仍是模型编写、未经独立核实的状态估计，使用原有 `facts`、`hypotheses`、`openQuestions`、`nextAction` 结构，不自动晋升为 Brain 长期记忆。来源观测可以作为假设保存，无须为满足合同把它伪装成事实，也不要求裁剪工具结果正文。

检查状态为 `not_required`、`needs_correction`、`satisfied` 或 `failed`。`satisfied` 只证明候选检查点符合交付结构和来源要求，还需要真实运行及清理终态；不等于领域结论已被独立核验。

## 5. 控制器与职责

模型负责读取授权来源、形成诚实工作状态并调用 `workingMemory` 保存；宿主负责权限、租约、持久审计、预算和完成门禁。宿主不能替模型生成 LOG，也不能为了通过验收编造证据、问题、工具调用或来源 ID。

共享的 `inspectWorkingMemoryCheckpoint` 检查当前候选，无需虚构 completed 运行。历史 resolver 在真实成功终态、owner 和任务范围检查后复用该校验，因此当前交付与未来继承采用同一来源标准。最新失败、清空、过期或不兼容的状态仍阻止继承，不回退复活更旧的检查点。

## 6. 控制动作与工具矩阵

| 动作 | 执行者 | 准入与回执 |
| --- | --- | --- |
| 读取当前版本和目录 | 模型调用 `workingMemory` read | 原权限与工具预算；读取不计为 LOG |
| 读取当前来源 | 模型调用原有授权读取工具 | 原 owner、scope、denied、approval 及租约边界 |
| 提交 LOG | 模型调用 update，phase=LOG | 实际 commandId、expectedVersion、完整 state、真实 catalog toolCallId；先持久审计再提交状态 |
| 候选交付检查 | 宿主 | 完整宿主快照与持久事件精确比对，记录 `working_memory_delivery_checked` |
| 一次有界纠正 | 模型在同一次运行继续 | 原预算内最多一次纠正 episode、四次额外 forward；发送前持久预算回执 |
| 一次有界上下文压缩 | SDK 通过宿主已授权的压缩入口 | 最多一次、最多 2048 输出 token；计入同一 8192 token 总 grant、420 秒和物理请求预算，压缩摘要不是最终交付 |
| 运行提交前复核 | 宿主 | 真实 runtime/cleanup 完成后重读持久事件，防止通过候选后状态变化仍误完成 |

普通 `workshopLogEvent`、最终报告中声称“已保存”、read、PLAN 更新、shadow 更新、旧继承记录和 restore 均不满足本轮 fresh LOG 合同。LOG 后执行 read 可以使快照 phase 显示 PLAN；只要完整 state、version 和 policy 与最新持久 LOG 一致，不应误拒。

## 7. 边界、审核与用户介入

`denied` 与需审批边界优先于 allowed。合同不添加领域工具，不绕过审批，不改变原有角色分工；没有 admitted apply-mode Harness、同 Work 的有效执行租约或可用工作记忆工具时拒绝运行，不能通过扩大权限补齐。

主人沿用桌面车间的任务运行记录、工作记忆和来源入口审核结果，通过现有暂停/停止能力中断运行，通过 Brain 纠错更新当前理解。尚未实际检查的页面状态不能标记已验收。审核应能分清“候选已核对”“任务已完成”“严格验证通过”，并能看到缺失 LOG、来源错误或辅助降级的具体原因。

## 8. 反馈与下一轮继承

首个最终候选缺少合格 LOG 时，宿主保留该候选为 intermediate，并反馈真实工具 schema 和缺口；反馈不授予权限、额外任务尝试或无限预算。最多一次纠正机会后仍不满足则失败，不显示 completed。

启用 fresh-source 后，每轮必须有至少一条真实当前来源绑定的笔记，以及真实未决问题或下一步。存在本轮主人/Brain 纠错时，历史 facts、hypotheses、nextAction 被抑制，因此必须保留真正未解决的 `openQuestions`；若确实没有问题，应报告 blocker，禁止为通过检查编造问题。

每个新 LOG 可以合法创建自己的新根。下一轮进入时必须精确继承上一轮实际根及其原 createdAt、expiresAt、rootHash；新 LOG 的新 TTL 不能伪称旧根续期。纠错后历史 `sourceRefs` 可以自然为空，fresh-source 证明取当前原 LOG 的来源审计；继承则核对被保留的问题、原根、父链和原 TTL，不以已抑制断言的引用数量误判。

## 9. 异常、扰动与降级

任何一轮执行失败、审计不完整、辅助 fallback、来源或版本不符、期限/工具/请求耗尽、用户取消、租约失效或源码漂移，立即停止后续轮次，保存已发生的请求和失败，不重跑该领域任务，不兜底更旧检查点。

保留既有显式官方 Go Qwen 不透明 SSE 恢复策略：整个 Harness 最多一次原样物理重发，两次共享 120 秒、4 MiB、20,000 帧限制；每次物理请求都计入本阶段上限。只允许该既定精确错误形状，不能恢复明确拒绝、鉴权、截断、EOF、网络或审计错误。物理恢复与自动领域重放分开，不能用“领域不重跑”掩盖物理重发。

## 10. 页面可观测性

本阶段以桌面 Web 的同一任务入口、等待状态、运行记录、工作记忆、来源追溯及失败原因可读性为验收范围。展示候选/提交检查、最终状态及辅助 warning，避免只显示已启动或保存次数。实际 UI smoke 与后台事件核验分开记录；本方案不新增移动端或原生客户端专项验收。

## 11. 数据、审计与回滚

复用原持久运行事件、工作记忆审计、Brain contextLog、运行快照与 Loop state，不新增业务数据库 schema。关键证据包括当前运行 accepted LOG、`source_checked`、projection、usage、候选及 runtime_commit 的交付检查、纠正 forward、runtime terminal 和实际辅助终态。

新阶段使用独立计划、幂等命令、来源封印、构建回执和轮次文件。原四次生产尝试、诊断、旧计划、旧代码快照及公共 JSON 均不可覆盖。公开证据只输出轮次、终态、时间、耗时、计数、来源类别、机制布尔及构建标识，不输出私有身份、正文或凭证信息。

失败回滚时先停止同范围执行，保存实际装载和配置基线，再通过版本化配置命令关闭合同或切回已审阅构建，并回读结果。回滚不删除已经保存的笔记、原始事件或旧失败；不得把恢复配置说成撤销了既有业务动作。主人保留暂停、纠错和重新授权权利。

## 12. 测试与严格验收

程序检查覆盖 opt-in/非法配置、LOG 后 read、未提交审计、shadow/PLAN/restore/旧继承、snapshot version/state/policy 不一致、真实来源 ID/hash/窗口/版本/时间、跨 scope、撤销、截断、TTL、纠错抑制、首次反馈及第二次失败。SDK 集成确认回调读取已提交宿主快照；文字声称已保存和审计失败均无法产生 accepted LOG。

生产验收必须同时满足：

1. 新构建与源码封印一致，正式 Web 和 worker 实际装载，唯一目标车间/Loop 范围和租约正确。
2. 每轮一次真实领域执行，主模型完整输出及 runtime/cleanup completed；所有实际主请求包含当前纠错的完整正文、精确版本、25 置信度、active 状态和未核实警告，旧版本排除。
3. 每轮真实 fresh-source LOG 与宿主快照、来源回执一致；候选和运行提交前检查均通过，不由宿主代写。
4. LOG2 初始继承 LOG1 实际检查点，LOG3 初始继承 LOG2 实际检查点，分别保留该父根原 TTL，并尊重纠错抑制。
5. 每轮 planner 与质量评估均真实模型完成，完整终态与语义结果相符；HTTP 成功或规则输出不充数。
6. 无越权、隐藏重试、虚构来源、静默截断、跨任务混合、失败后回退或将 unknown 用量补零。

## 13. 分阶段执行与停止条件

新阶段最多 **3 次领域尝试、54 次物理模型请求**；每轮最多 **18 次物理请求、420 秒、14 次工具调用**，每轮一次领域执行，没有自动领域重放。一次宿主纠正 episode 最多四次 assistant forward；上下文压缩最多一次、最多 2048 输出 token，包含在同一 8192 token 总 grant 内。纠正、压缩和既定原样物理恢复均消耗原时间和物理请求预算，不新增额度。旧四次领域尝试、29 次生产物理请求和五次认证诊断另列，不归零或挪作本阶段成功样本。

顺序固定为：冻结源码与新工具 → 类型/针对性检查 → 构建 review94 → 正式装载与无任务预检 → LOG1 → 独立审计 → LOG2 → 独立审计 → LOG3 → 最终独立审计。没有当前轮严格通过证据就不排下一轮；失败即停止，不加第四轮或重跑失败任务。

最终交付分别说明已编辑、程序验证、生产装载、每轮任务结果、记忆贯通结果、辅助健康、实际消耗及遗留问题。若只完成构建或部分轮次，结论明确为尚未完成三轮验证，不能承诺已经解决生产问题。

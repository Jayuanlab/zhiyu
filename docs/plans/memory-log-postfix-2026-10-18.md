# LOG 保存与两轮连续生产复验补丁方案

本方案继续执行主人 2026-10-18 的授权。原 LOG 阶段第一轮实际失败，消耗一次任务尝试和 17 次物理模型请求，保留原始报告、源码和严格失败判决，原 LOG2、LOG3 不再启动。下面的两轮属于同一授权中剩余的两次尝试，不增加原定总预算。

## 真实问题与有限修复

1. 当前行配置已经启用合同，但执行器优先读取旧持久 `loopSpec`，导致结构化模型输入遗漏新字段。只对这个合同采用当前行配置；已撤销的合同也不能从旧状态复活，其他历史字段保持原语义。
2. LOG 已保存，笔记正文仅 1,074 字符，但多个笔记反复展开同一份完整来源信息，未应用纠错的传输表示超过 8,000 字符，交付检查错误拒绝。分开保存证明和实际传输检查：来源仍完整核验，实际纠错后的继承表示仍执行原上限，不截断来源，不提高历史传输限额。
3. 一次有界修正的最终回复触及长度上限。保留一次修正、四次报告转发和整轮期限，修正总输出上限改为 16,384 token，并要求短报告和紧凑结构化结果。一次至多 2,048 token 的压缩仍包含在同一总额度内，不能续期或重置。
4. 质量评估收到完整 JSON，但严重性枚举不合法，降级为规则评估。明确列出模型必须使用的枚举及字段类型；非法内容仍失败，不能映射成成功或追加模型重试。

## 闭环与边界

| 项目 | 本阶段约束 |
| --- | --- |
| 被控对象 | 同一车间、同一 Loop 的 LOG 交付、当前纠错召回及下一轮状态继承 |
| 观测 | 正式 HTTP、实际 worker、模型传输终态、持久事件、已提交宿主快照、来源窗口和版本 |
| 状态 | 当前配置、不可变原始事件、模型笔记、宿主交付证明、终态和跨轮检查点分层保留 |
| 动作 | 构建新生产候选、核对实际装载、逐轮运行 FIX1 和 FIX2；第一轮独立通过才启动第二轮 |
| 权限 | 不扩大工具、角色或外部动作；denied 与审核规则继续优先；没有消息外发、交易或待发草稿 |
| 反馈 | 保存不等于交付，交付检查不等于任务成功；完整运行和清理终态后再次回读审计 |
| 异常 | 不完整响应、来源冲突、租约丢失、审计失败、超时及不合格检查点均显式失败 |
| 人工控制 | 桌面车间的运行记录、记忆及 Loop 页面继续提供审阅、暂停、取消与纠错入口 |
| 回滚 | 停止新进程，使用保留的构建及来源恢复；配置撤销走版本化命令，失败与历史笔记不删除 |

新阶段 `memory-log-postfix-20261018` 最多两次任务尝试、36 次物理模型请求。每轮最多 18 次请求、14 次工具调用、420 秒、一次领域尝试；无自动任务重跑。原 LOG 阶段实耗 17，加本阶段最多 36，合计最多 53，仍小于原授权阶段的 54。连同更早的四次任务、29 次生产请求，最高七次任务、82 次请求，仍在原有七次、83 次累计上限内。五次更早的认证诊断单列。压缩、修正和有限传输恢复都计入实际请求总数。

FIX1 必须看到最近一次 LOG1 的真实失败状态，不从失败笔记或更早检查点回退继承；重新观测来源并保存真实新 LOG。FIX2 必须继承 FIX1 的确切根、原始创建时间和原 TTL，同时进行一次真实新来源观测并保存本轮 LOG。每一份实际主请求必须包含当前完整纠错正文、真实置信度和状态，以及结构化合同；至少一次成功任务自主展开 typed owner 来源。两条辅助链路须实际完整结束。

程序验收覆盖保存证明与实际传输的分离、无纠错时仍拒绝过大表示、纠错后未决问题本身过大仍拒绝、错误来源 hash/窗口/版本仍拒绝、配置开关与旧状态冲突、非法质量枚举、实际提交快照、期限与租约边界。生产验收保留实际模型请求、独立审计及桌面可读性检查。实际构建、装载和两轮结果另写验收报告，不能用离线重放替代。

实际执行结果见[生产验收报告](../verification/memory-log-production-2026-10-18.md)：FIX1、FIX2 的保存、纠错召回和跨轮继承机制检查通过，两轮共 21 次物理请求；严格总验收因成功轮次未自主展开 typed owner 原始证据而保留失败。后续 P2 桌面改进包括最新 Loop 记录定位、终态与目标映射、继承提示可读性，不算本阶段已完成项。

# 记忆系统：智能体对自身及可访问世界的可靠信息访问

## 用户目标与可验收定义

本轮用户将目标扩大为“把记忆系统做好，智能体通过它知道所有想知道的，包括自身和可访问外界”。这要求建设信息访问和状态估计系统，而非继续单独优化 Jev。所有可访问不等于绕过权限，也不代表未知事实可以生成。

验收按信息需求逐项检查：已存在可访问证据能定位；动态事实读取当前权威来源；历史事实有版本及有效区间；外界信息通过已授权连接读取；结果标明来源、时间、覆盖范围与冲突；找不到时区分缺失、无权限、不可用、过期和未检索，并给出可执行补齐路径。

## 控制闭环

- 被控对象：智能体每次回答/行动前的信息状态及其证据完整性。
- 观测：当前运行工具与身份、平台记录、长期记忆、文档、原始事件、公开网页和已授权连接；检索时间与事实有效时间分开。
- 状态：既有 Brain 原始观测、候选、正式记忆、ContextPack、工具轨迹及车间事件；新增统一查询返回结构，不建立重复事实库。
- 动作：只读定向查询、来源展开、请求补充、形成待审核记忆候选。写入沿用审核与幂等机制；读取不得暗中变更权限、配置或发送消息。
- 边界：复用最终授权工具句柄，不能从统一入口构造 owner 级读取器绕过车间权限；denied 优先；内网与外网查询分开，不自动外传私人内容。
- 反馈：记录每域返回、缺口、重复抑制、预算耗尽和源失败；下一次使用原证据或收窄查询，不能循环扩大读取。
- 降级：独立来源失败不抹掉其他证据；无历史版本不读当前值冒充；没有连接时明确缺少适配器。
- 人工接管：沿用对话澄清、记忆候选审核/纠错、车间暂停与访问授权界面。无新增自动写入或后台任务。
- 页面：统一查询工具结果显示来源状态和限制，已有诊断详情可追溯；后续需要针对实际桌面流程完善缺口可视化。
- 验证：权限穿透、来源范围、分页冒充全量、历史替代、重复读取、取消、部分失败、外网隐私隔离、自身能力与实际授权一致。

## 实施顺序

1. 访问底座：统一查询入口、自身运行能力目录、既有来源组合、预算和可观测缺口；修复来源自动扩展与列表完整性元数据。
2. 精确读取：全量聚合与受控分页、明确记录/文档展开、历史快照按类型与有效区间读取；不能仅凭数量限制把结果叫全量。
3. 获取与沉淀：授权外界连接、原始观测留存、证据版本/冲突/纠错闭环；外界读取成功不直接升级成已验证长期事实。
4. 跨入口验收：桌面对话与持续车间都走权限约束；自我、用户、任务、知识、经历、当前外界、历史状态组成独立测试集，覆盖多轮及失败恢复。

Jev 是可替换的辅助判定，不是信息完整性的证明。保留此前失败与弃权结果；不通过降低门槛替代系统改进。阶段通过不等于“所有信息都已覆盖”。

## 本轮实施状态

访问底座已落地到桌面 Pi 和受工具清单约束的 Pi 车间；公开页面读取、关键词降级、运行主体投影、统计列表执行限制及所有者/Work 记忆身份已实现。真实验证发现并修复了目录冒充权限、本人记忆被误拒、文档报错伪装空结果、网页片段被前文截断以及重复读取问题。

补充固定白名单的平台实现读取，直接访问记忆权限、选择、召回等实际代码，带行号与哈希；模型不再需要从源路径猜远程仓库地址。内部可选发现路径也受到显式来源范围约束，模型规划不能扩大范围。

检验记录见 [实施与真实验证](../research/memory-system-access-validation-2026-09-23.md)。不能把控制约束召回当作主题相关答案；语义检索恢复、历史版本读取、独立真实问题覆盖与完整跨轮任务验收仍未完成。原始观测和审核写入机制复用既有系统，本轮没有开启未经验证的自动记忆晋升。

## 第二阶段：证据展开

本阶段控制对象是检索后的证据覆盖范围：askMemory 接受文档 ID / 已公布源码 ID，仍只委托调用方最终授权的只读工具，不新增数据库越权通道。文档通过所有者检查后，按 8,000 个 UTF-16 单元返回片段、哈希、下一位置和读取时间；续读可携带上一哈希，变化则明确停止拼接并提示重读。它是当前版本读取，不是历史版本库；底层仍复用现有全文加载器，未声称数据库内存读取已分页。

统一返回请求域、实际观测域和读取缺口，完整性保持 not_verified；该信号供模型继续读取或明确缺口，不能将“工具调用完成”当成所有用户需求已覆盖。只读轨迹复用现有审计和工具详情，用户仍可检查出处并纠正回答，没有自动记忆写入。异常分为权限/缺少工具/版本变化/预算耗尽；测试验证越权拒绝、版本不混用、分段重建和真实读取范围说明。完整自然问题的需求拆分与精确引用仍是后续验收项。

该阶段已完成实现、81 项针对性测试、开发环境和生产构建 89 的源码读取回归。当前所有者知识库为空，非空真实文档续读验收仍缺数据，未标记通过。详见 [证据展开验收](../research/memory-evidence-expansion-validation-2026-09-23.md)。

## 第三阶段：已保存快照的精确访问

控制对象是历史问题的证据选择。已有快照保存内容、来源记忆 ID、作用域和创建时间；本阶段增加 snapshotId 精确读取及 recordedBefore 数据库筛选，不能将最近一条旧记录解释为目标时刻的全量状态。状态继续保存在原快照表，不回填或伪造缺失历史；时间字段仅按保存时间解释，事实有效区间仍需独立证据。

只读动作由现有 brainListSnapshots 和 askMemory 执行，按 ID 分段展开使用版本哈希校验。所有查询保留 authenticated owner 过滤；Work 调用强制绑定其自身 work 作用域，不接受模型替换读取主体或通过 ID 扩大权限。未找到、版本变化、非法时间、空过滤条件均显式返回，缺口不能触发当前状态替代。工具轨迹和结果详情沿用桌面/车间既有审计，用户可查看出处、纠错及暂停车间；没有新写入、定时任务或隐式授权。

验收覆盖作用域、精确 ID、时区与非法日期、分段版本一致性、找不到记录与工具失败区分，以及真实历史查询。跨作用域授权快照共享和任意历史时刻状态重建不属于本阶段已实现能力。

真实回测发现旧快照使用 workshop 作用域，因此“自身 Work”同时包含同 ID 的 work / workshop 两种存储类型；其他主体和全局作用域仍不在读取范围。实现与证据见 [历史快照读取验收](../research/memory-snapshot-access-validation-2026-09-23.md)。

## 第四阶段：发现范围与能力结论分离

控制对象是智能体对“找不到”的解释。最近快照列表是有界样本，不足以证明全部类型；新增 view:catalog 在原快照表按类型聚合数量及最早/最近保存时间，复用所有者、Work、时间和类型条件。最多返回 100 种类型，超过时明确截断；单次聚合以数据库读取为观测，不新增缓存状态和后台扫描。

目录仅证明本次权限/过滤范围中的已保存记录数量，不能推导内容包含何种事实、删除或不可访问历史、全部平台能力。当前统计读取器 unsupported_time 也明确限定到该读取器，并给出目录→类型筛选→精确快照的恢复路径。失败不等于空、样本不等于目录、记录类型不等于内容语义。读操作继续由最终工具权限和现有审计控制，用户在工具详情看来源与范围，无配置变更或自动写入；对超出证据的模型结论仍需真实回归，不能只靠新增提示即宣布解决。

生产验证发现模型改写查询可清除历史限制，补充将原始用户时间意图从桌面运行时可信传入读取器，不能由工具参数覆盖。统计读取和证据时间校验使用同一约束。详见 [目录与能力范围验收](../research/memory-snapshot-catalog-validation-2026-09-23.md)。

## 第五阶段：重复观测与内容覆盖

控制对象是同一工具实例内的重复目录读取及其证据解释。成功目录按用户、Work、时间、类型过滤键复用至多 30 秒，最多保留八项、每项正文不超过 64,000 字符；保留原覆盖时间并返回 readReuse，明确没有重新查询数据库。状态只在工具实例内，不新增共享缓存或持久化副本。精确记录、版本校验续读和列表不复用；refresh:true 可明确获取新观测，失败则暴露错误，不回退旧成功结果。

复用放在已有权限检查的 handler 内，重复调用仍经过外层授权和审计，不能从缓存绕过拒绝。目录新增 contentCoverage，显式标记只读取类型元数据、正文读取数量为零、支持与不支持的结论范围。反馈用于决定继续定位具体记录或报告识别缺口；不把元数据目录变成内容不存在的证明。用户通过既有工具详情查看复用来源和原时间，无新增后台动作。测试覆盖过期、刷新、失败、键隔离、空间上限、权限拒绝与真实重复读取；模型是否真正停止按类型猜测内容仍须独立回测。

第五阶段已通过 92 项相关测试、构建 80 与真实生产复用验收；自然历史问答仍有内容推断错误，未标记整体通过。详见 [目录复用验收](../research/memory-catalog-reuse-validation-2026-09-23.md)。

## 第六阶段：快照正文证据检索

控制对象是从类型发现到原始内容验证的缺口。brainListSnapshots(view:search, contentQuery) 在数据库对快照 content 的 JSON 文本执行参数化字面匹配，LIKE 特殊字符按字面转义；与用户、Work、时间、类型条件合取。askMemory.reads 的 snapshot_search 复用该授权工具，不创建第二套数据权限。

每次最多十条候选，每条返回至多 1,200 字符上下文、来源 ID、保存时间及整条快照哈希；额外读取一条判断是否仍有匹配，不把限量结果当全量计数。哈希可用于精确快照读取的 expectedHash，来源变化后不能拼接旧证据。查询仍是只读审计动作，复用现有详情界面；不写入新的长期事实或启动后台任务。

JSON 字面匹配包含字段名和值，不是语义检索，也不是正确性证明；无命中只说明该词组在该范围未匹配，不能推导事实不存在。失败单独返回，不能假装零命中；匹配片段仍需展开并核对上下文。测试覆盖权限条件、通配符转义、参数化、范围与截断、空结果/失败区分及统一入口接线；真实回测检验由正文命中到版本一致展开，不以类型名作为事实依据。

该阶段通过 96 项相关测试、构建 78 和真实生产正文搜索→哈希展开验证，详情见 [正文检索验收](../research/memory-snapshot-content-validation-2026-09-23.md)。缺少目标标识的历史统计仍报告缺口，未伪造匹配快照或数字。

## 第七阶段：正文搜索的有界连续读取

控制对象是搜索返回更多匹配时的覆盖缺口。新增 nextCursor/cursor，按 createdAt、ID 降序执行数据库 keyset 查询，不使用可能漂移的 offset。第一页固定搜索时间上界；续页保留数据库原始时间精度，避免 JavaScript 毫秒日期截断 PostgreSQL 微秒后跳过记录。每页仍强制所有者/Work/内容/类型/时间条件，游标包含查询指纹防止误用于另一查询，且不能扩大显式时间上界。

游标只是续查元数据，不是授权凭证；每页照常执行权限及参数检查。实例不保存全量搜索结果，不写数据库；原有工具轨迹记录页请求与返回，用户可查看每页来源和剩余页状态，或停止继续读取。askMemory 把游标纳入去重键，正常续页不会被误认为重复请求。

该机制稳定排序和排除较新的插入，但不是跨请求数据库事务：更新、删除、回填旧日期记录仍可能改变结果，必须明确披露；到达末页只表示本次字面检索没有后续页，不证明语义完整。异常游标、查询/主体变更、缺失排序位置都显式失败，不退回第一页。测试覆盖多页无重复、精度、固定上界、范围绑定、非法游标和统一入口续读；真实验证读取多页并保留还未读完的状态。

第七阶段通过 104 项相关测试、构建 76，以及开发和生产各三页的真实读取验证。原始工具输出确认六条无重复、时间上界一致且仍有更多匹配。详见 [连续分页验收](../research/memory-snapshot-pagination-validation-2026-09-23.md)。下一步仍需验证自然问题到证据定位的准确率，不能将明确指定工具参数的接口验收当作整体记忆能力完成。

## 第八阶段：自然问题的证据核对

控制对象是评测的误判：流结束不等于正确，回答包含一个 UUID 不等于角色正确。以不指定工具的自然问题触发只读生产链路，保存原始 SSE、最终回答与工具结果；离线核对最终回答中的 UUID 在受支持原始记录中的字段路径。状态保存在评测目录，保留历史文件，新增审计文件可重算；不写 Brain、不向模型传入答案或审计标签。

评测分别记录 finalAnswer、工具输出字符数及字段出处。排除问题回显、requestedIds、失败结果和自由文本；只读取已知记录结构，部分原文窗口及未知结构保留未验证。字段存在不能证明角色、时间或语义正确，因此始终 requires_claim_review，不自动给正确率。测试验证回显污染、失败、缺失最终回答、原文窗口及 ID 字段角色。用户可通过评测文件核对和纠正，不引入自动任务或外部动作。

本轮两道自然问题验证了真实失败记录发现和 Work 标识识别，但第二题把 runId 泛称为事件 ID，且第一题读取 131,520 字符工具输出。不能宣布自然问答整体通过。下一优先级是 platformRecall 的有界发现与精确续读，以及 Run/事件标识区分；详见 [自然问题证据核对](../research/memory-natural-evidence-validation-2026-09-23.md)。

## 第九阶段：快照发现输出收敛

控制对象是 platformRecall 的 brain 发现分支将整批快照正文送入上下文。保留数据库原权限查询，最多发现五条，每条只暴露 1,200 个 UTF-16 单元的原文片段、全记录哈希和精确读取参数；额外查询一条仅用于标记更多结果。不新建缓存或事实，不自动写入或执行任务。原始快照及版本由数据库保管，工具轨迹保存发现片段，用户可检查来源、要求展开或停止读取。

截断显式披露，近期样本不等于全历史，无命中不等于事实不存在。精确读取走既有 brainListSnapshots 权限和 expectedHash 校验，失败不回退旧原文。提示明确 Run、Loop、Work 和 eventId 各自独立，不从 UUID 格式推断角色；提示不能替代真实问答验收。测试核对大正文输出上界、哈希与精确展开兼容、额外记录不泄露及查询权限；开发和生产均回测自然问题。当前改动只约束快照发现，不宣称其他 platformRecall 分支或整体输出已受统一预算限制。

第九阶段通过 61 项针对性测试、构建 74 以及开发/生产发现→哈希展开验证。brain 分支实际输出从 74,654 降至 9,138 字符；自然题仍有重复查询及部分语义泛化，整轮预算未通过。详见 [快照发现输出约束验收](../research/memory-snapshot-discovery-validation-2026-09-23.md)。

## 第十阶段：共享读取预算

控制对象是桌面 Native Pi 的证据读取，以及使用相同工具实例的 askMemory 委托读取。预算包装在权限检查后的 handler 内，每个工具实例最多十次实际尝试，单次格式化证据至多 24,000 字符，累计至多 64,000 字符。并发完成时检查并提交字符支出，避免重复消费余额；失败也计入尝试次数。参数规范化后的完全相同读取不重复执行，游标、偏移和版本参数保留在键中；目录允许原有复用与刷新，返回内容仍计入预算。

状态仅存于请求实例，不跨用户、请求或车间缓存原文。超大结果整份扣留并明确报错，建议缩小查询或使用精确分页，不静默截断或伪造完整证据；失败后可有限重试，超限与重复情况通过原守卫写错误轨迹，权限拒绝优先。用户可查看工具错误并在新请求中缩小问题；没有自动写入、配置变化或外部动作。

预算只覆盖明确列出的读取工具，未覆盖静态 manifest 工具、其他自定义车间工具、错误消息开销或模型自身输出；不是整个智能体的 token 硬上限，也不限制一次读取在服务端产生结果的成本。Work 复用 Native 实例时继承这些工具的预算，但其自定义工具尚未合并。测试覆盖权限优先、直接/委托共享、并发累计预算、来源失败重试、继续分页和请求隔离；开发与生产验证超限恢复及自然问题。没有证据时仍须报告缺口，不能把预算错误解释为不存在。

第十阶段通过 95 项测试、构建 71 和生产重复拒绝→精确恢复验证。生产自然题找到目标记录，成功交付证据 49,023 字符，第十一次读取被阻止；仍存在找到答案后继续查询的问题。详见 [共享读取预算验收](../research/memory-read-budget-validation-2026-09-23.md)。后续优先改进证据足够时的停止条件，并继续区分主要结论通过与衍生语义未验证。

## 第十一阶段：完整快照后的回答核对

控制对象是精确展开后缺乏明确的回答/继续读取决策节点。只有单次成功返回整个快照且版本校验通过，才附加 answerCheckpoint；部分窗口、失败、版本变化不触发。读取节点绑定桌面运行时的原始问题，工具参数不能重写它；复用已有问题拆分器，保留未解析义务，并明确任何长度截断。缺少原始问题的入口仅提供通用核对，不假定已覆盖需求。

节点报告已读来源及字段可用状态，不判断相关性或答案完整。null 明确是未记录数值，不能解释为零、未完成或成功。模型应逐项核对问题：若只需一个例子且记录支持全部要求，则停止搜索并回答；只有具体未回答条款、时间条件、矛盾或原文缺页才继续。比较、最新状态、全部记录等需求不能因读到一个快照被强行截断。结构由代码生成，原始证据仍是不可信数据，节点不执行证据中的指令。

状态随工具结果进入既有审计与详情，用户可纠正问题或要求更多证据；不写长期记忆，不修改工具权限，硬预算继续兜底。测试验证完整/部分/版本变化分支、原始问题绑定和 null 状态；真实题验证展开后能否及时回答，同时记录失败样本，不用停止提示替代语义正确性评估。

第十一阶段通过 69 项针对性测试和构建 69。生产单例题三次调用后结束，完整展开后无额外读取，输出 13,033 字符；复合题保留恢复状态缺口，但另一读取入口仍出现 null 语义过度推断。详见 [回答核对验收](../research/memory-answer-checkpoint-validation-2026-09-23.md)。下一优先级是精确平台记录的有界展开：已观测到查询 runId 时 limit 降为 1 仍超预算，导致后续状态查证受阻；同时将字段状态解释扩展到该入口。

## 第十二阶段：精确平台记录的有界展开

控制对象是 platformRecall 对指定 ID 同时读取多类记录和一跳关联后，响应超过读取预算。这里的 `limit` 仅约束列表，不约束精确记录的正文，导致模型反复缩小 limit 也不能恢复。改为最多发现八条记录，每条大记录仅返回固定标识/状态字段、完整记录哈希及展开参数；超出条数明确报告遗漏引用和截断状态。精确展开采用固定来源名和 UUID，重新执行相同所有者查询，按 8,000 UTF-16 单元分页；版本变化返回失败而非拼接。

原始记录仍在现有数据库，投影只是一次观测，不能当作全部字段。控制动作是用户或模型凭返回引用进一步读取，无后台扫描或长期记忆写入。权限由既有工具守卫和来源查询双层执行，未知来源、不属于该用户的 ID 均失败；拒绝优先于允许。审计保存每次发现、精确读取、版本变化和预算错误。失败时须报告权限/来源/预算缺口，不将“未展开”解释为字段不存在；null 标记未记录，不解释执行过程。

回测检查大原文不会把完整响应挤出预算、关联记录优先级、哈希续页和所有者隔离，以及真实 runId 问题是否能定位执行状态与后续恢复证据。精确记录本身的记录时间不是后续状态有效区间；找不到同一 run 的后续记录时，只能说当前范围未验证恢复。用户通过既有工具详情检查来源与未读页；范围仍是桌面 Web 与必要后端。

实施中发现两类提前作答：模型把发现投影的隐藏字段列为“建议展开”却不读，以及精确读取第一页后把局部内容误当完整原文。现分别返回 `pendingExactReads/completionGate: exact_record_read_required` 与逐页 `completionGate: record_read_continuation_required`，末页才是 `record_read_complete`。所有完成标记只覆盖固定发布字段，不能证明数据库全部列、完整外部日志或后续恢复。开发自然题已完成五页重组；生产回测与语义审查详见 [精确平台记录有界展开验收](../research/memory-platform-record-expansion-validation-2026-09-23.md)。

第十二阶段最终 61 项针对性测试、独立类型检查和生产构建 63 通过。真实宽泛 runId 问题在生产完成发现加五页精确读取，零工具错误、哈希审计重组成功；答案仍对未展开的关联名称及后续处置作了推断，因此只验收了读取闭环，不验收整体语义正确。下一优先级是答案主张与已读字段、时间和动作结果的逐项匹配，并补充按 Loop ID 检索后续运行的受控入口。

## 第十三阶段：按 Loop 查询后续运行

控制对象是“历史 run 后来是否有新运行”的证据缺口。单条 run 与关联 loopStates 只能说明已记录的那次运行及状态行，不能代替后续运行时间线。观测输入为所有者可见 Loop、基准 run、后续 loopRuns 的固定发布摘要；服务端先校验 Loop 所有权，再校验基准和续页 run 均属于该 Loop。使用数据库原生 `(created_at,id)` 顺序比较，避免时间戳经过 JavaScript 毫秒精度往返后把基准 run 误算为后续；若返回基准、游标或乱序页，显式失败。

状态在原有 loop_runs 表中，不复制为新记忆。控制动作是只读有界查询：每页最多八条，返回 `hasMore` 与 `nextCursorRunId`，后续页再次检查所有者和游标；精确验证仍由既有 `recordRead` 展开。对明确问“后来/恢复”的精确 runId 查询，平台服务自动读取第一页时间线，避免模型把待执行建议直接当最终答复。来源异常、权限不足或页边界异常均作为失败暴露，不能说“无后续运行”。用户可从工具详情核对基准、读取时间、排序、每条 run 和未读页，随时停止续查。

反馈信号是页数、错误、答案中是否区分“后续运行存在”“后续运行完成”“原失败已修复”。`completed` 仍不能单独证明修复，必须进一步核对后续 run 的验证结果；`hasMore=false` 仅代表本次读取时所有者可见范围内到达末页，新插入或回填会改变以后读取。针对性测试与真实数据库回测必须覆盖同时间戳排序、跨用户拒绝、错误游标、基准自我返回和自然问题答复；语义主张仍需人工核对，不能以字段存在代替正确性。

第十三阶段完成受控时间线与自动首读，生产构建 61、独立类型检查和 67 项相关测试通过。真实生产问答对指定失败 run 返回零条后续运行、末页、零工具错误；先前开发版本把基准 run 错算为后续的失败样本已保留，数据库内元组比较和页不变量随后修复。详细证据见 [Loop 后续运行时间线验收](../research/memory-loop-run-timeline-validation-2026-09-23.md)。下一步应建立答案主张与实际字段/时间/动作结果的核对，尤其防止把旧状态、未展开名称、工具允许或建议操作写成当前事实或已执行动作。

## 第十四阶段：平台回答的证据主张边界

控制对象是模型把旧持久化状态写成当前执行器运行态、把 `present_unread` 字段值猜出、把工具允许判定说成动作已执行、或把后续运行状态当成原故障修复。观测输入来自 owner-scoped 平台记录投影、Loop 时间线和精确读取；`loopStates` 不论短发现还是精确读取都注明最后持久化时间与 `currentRuntimeVerified:false`。状态不写新的长期记忆，而是在本次 `platformRecall` 响应中生成 `claimBoundary`，分别标出读取时后续运行覆盖、未观测的实时执行态、未证实的修复状态、未读字段和权限判定的语义上界。

控制动作只是约束本次回答：模型应给出最后持久化状态及 `updatedAt`，并将实时态与修复判断标成未证实；需要新证据时才走有权限的读取工具。预取与普通平台提示都引用这组边界；`recordRead.source` 的工具模式列出固定来源名，阻止模型用 `runs` 之类的泛称冒充数据源。离线评测追加保守的 `claimRisks` 人工复核信号，区分肯定/概率性的实时推断与问题标题、否定句。它不自动判语义正确，不修改最终回答，不越过用户审核。

反馈是原始工具轨迹、时间线窗口、最终答案与人工主张复核。来源失败、超预算、未读字段或缺少实时观测时不能用推断补齐；自动审计只提示风险，不能伪造无风险等于正确。测试覆盖短/精确状态时间标注、权限与执行区分、固定来源模式、否定句不误报及真实历史 run 问答；完整生产结果和遗留语义问题记入阶段验收。

第十四阶段七文件 89 项针对性测试、类型检查和生产构建 59 通过。真实生产问答仅一次 owner-scoped 读取且无工具错误，回答区分最后持久化状态、读取时间、未观测的实时执行态和未证实的故障修复；离线审计未提示明显的实时态越界句。早期漏查、来源猜测、概率推断和答案未完成的失败样本均保留。详见 [平台回答证据主张边界验收](../research/memory-platform-claim-boundary-validation-2026-09-23.md)。下一阶段需要真实实时执行器/心跳来源和更广泛的主张级验证；当前边界只是阻止把旧状态说成实时事实，不能替代对世界状态的实时观测。

## 第十五阶段：Loop 执行租约的限时观测

被控对象是回答把历史 `loopStates` 误当执行器现状。观测输入来自所有者可见的 Loop、活动关联的 Work/Loop run、Work run 状态，以及数据库时间、执行租约和心跳。先校验 Loop 所有者，关联查询再次加所有者条件；没有关联行时再次确认所有者仍可见。状态只在本次 `platformRecall` 响应中形成结构化 `runtimeObservation`，不写入长期记忆，也不改变运行租约。

控制动作是按单个 `loopId` 的只读 `runtimeRead`，或对明确询问当前执行器且已发现精确 Loop 记录的问题自动读取一次。仅在关联 run 匹配、Work run 与租约均为 running、租约在数据库读取时间尚未到期、心跳在两分钟内且未超前时，标记 `active_lease_recent_heartbeat`；这仍只说明读取时有近期受栅栏保护的租约，不保证回答瞬间进程存活、动作成功或历史故障修复。无活动关联、心跳陈旧、租约过期、所有权变化及来源失败都显式区分；不输出 worker ID、栅栏 token 或原始执行内容。用户可核对观测时间和字段，停止后续读取，仍由原控制界面审核、暂停及纠错。

反馈是每次观测的 provider、时间、关联 run、匹配/新鲜度和 warning，以及原问答轨迹。异常时不推断进程已停止或故障已修复。针对性测试覆盖跨用户、读取中所有权变化、近期/陈旧/未来心跳、过期租约、错配 run、完成的 Work run 与敏感字段不外露。真实只读查询、自然问答和生产构建结果见 [Loop 实时观测验收](../research/memory-loop-runtime-observation-validation-2026-09-23.md)。后续需更广泛的来源健康度和主张级验证。

第十五阶段三文件 33 项测试、独立类型检查和生产构建 58 通过。真实只读查询返回该历史 Loop 在读取时无活动关联执行；匹配构建的生产问答主动调用 `runtimeRead`，零工具错误，回答保留了最后持久化状态、租约观测与故障修复的区别。首次回测误连旧 `.next` 的结果已保留，不计入验收。仍需扩大到其他 Loop、来源故障和用户真实问题的语义回归；本次租约读数不是进程在线证明。

## 第十六阶段：观测来源故障与回测证据闭环

被控对象是来源失败被解释为“没有活动执行”，以及离线审计遗漏真实工具结果或把流式完成标记当成最终回答。观测输入为权限受控的单 Loop 租约查询、工具原始事件、最终结果及文本流。应用层对显式 `runtimeRead` 和自然问题自动读取的失败都返回 `source_unavailable`、provider、warning 与 `claimBoundary.currentExecutor.observationStatus`；历史记录可保留，但实时态不可由其替代。状态只在请求结果和离线评测中，保留原始事件供重放，不写入长期事实。

离线审计支持直接返回的 `timelineRead`、`runtimeRead`，记录观测时间和来源；仅当 `result` 是完成标记时才从文本流恢复可见答案。审计只给保守风险提示，仍需人工逐项核对事实、时间与权限。控制动作限于只读查询、测试和审计；不启动 Loop、不修改租约、不执行外部动作。来源异常、所有权不匹配、无关联执行分别保留不同状态。用户可在评测目录检查原始事件、暂停验证并纠错。

反馈信号是来源失败标记、审计捕获的时间线/租约窗口、漏记数量、最终文本风险及真实 DB 权限结果。针对性测试和原始事件重放见 [来源故障与审计验收](../research/memory-runtime-source-audit-validation-2026-09-24.md)。后续仍需扩大活跃租约样本及长期回归，不能把空租约样本当作所有执行状态的覆盖。

第十六阶段四文件 46 项测试、独立类型检查及生产构建 57 通过；原始生产事件重放纠正了直接时间线和租约结果的漏记。匹配构建的新生产问答零工具错误，审计记录精确 run/状态、空后续运行窗口及无活动关联租约，人工核对回答没有把旧相位或空租约说成实时停机。两个额外 Loop 的真实只读查询验证了所有者边界。仍缺运行中租约的真实样本和更广泛的答案语义回归。

## 第十七阶段：直接 Loop 问题的实时观测入口

被控对象是用户给出 Loop ID 问“现在是否运行”时，平台虽能查到 owner-scoped `loops` 记录，却不会自动读取执行租约，导致模型可能把任务的 `status=active` 当作执行器现状。观测输入为固定来源的精确 Loop/Loop 状态/run 记录及其请求 ID、随后按单个 owner-visible Loop 读取的数据库租约/心跳。状态留在本次平台召回与原始工具轨迹；任务配置、最后持久化相位和读取时租约分别标明，不写新的长期事实。

控制动作仅是只读定向读取：请求 ID 与 `loops`、`loopStates` 或 `loopRuns.loopId` 建立唯一 Loop 目标时自动读取一次；同时请求多个不同 Loop 时不任选一条，而返回逐个 `runtimeRead` 的参数计划。由于模型也可能直接调用 `runtimeRead`，该入口在同一所有者校验下返回 Loop 的配置 `status/updatedAt` 与租约观测，标明二者不同时间含义。权限在精确记录网关和租约读取器两处各自校验；来源失败、无活动关联和多个待读 Loop 不混为同一结论。用户可在工具详情检查目标 ID、观测时间、来源与警告，继续逐条读取或停止。

反馈包括自动读取是否触发、是否出现目标歧义、租约新鲜度与最终答案的时间边界。针对性测试和与隔离构建匹配的真实自然问答记录在 [直接 Loop 实时观测入口验收](../research/memory-direct-loop-runtime-validation-2026-09-24.md)。不启动 Loop 或调度器；活跃租约仍只在模拟测试中验证，真实在线性不能从无租约样本推断。

第十七阶段精确 Loop ID 自动目标、多个目标续读计划及同源配置/租约投影已实现，49 项相关测试、类型检查和生产构建 53 通过。真实单 Loop 问答一次召回、零工具错误，能取到配置 `active` 与读取时无活动关联映射；然而模型仍偶发将“租约未评估”改写成“未观察到租约”。离线审计已能区分真实越界和否定引用，最终生产样本有一条越界风险，故本阶段问答语义验收**未通过**。下一优先级是在在线输出链路做结构化主张校验与保守降级，并验证不破坏流式交互和用户纠错；不能把审计提示当成已经阻止了错误回答。

## 第十八阶段：直接 Loop 实时问答的在线证据闸门

被控对象是 Pi 已取得结构化运行观测后，仍在给用户的流式文字中将“租约未评估”写成“未观察到租约”，或将读取时的近期心跳写成回答瞬间必然在线。观测输入只取本轮、同一精确 Loop ID 的 owner-checked `platformRecall` 成功工具结果及其数据库观测时间；回答文本作为待验证输出，不反过来充当事实。状态限于单次请求中的工具 ID、最新有效观测和有界文本缓冲，不沉淀为长期记忆。

控制动作只作用于桌面 Web 的普通 Pi 问答：工具调用、工具结果、错误和心跳继续流出；单 Loop 当前运行问题的文字暂存至完成，检查越界主张。无有效观测、越界句或缓冲上限触发时，按可核对字段生成保守答复，并在服务日志中记录替换原因；正常回答原样放行。多个 ID、历史问题、其他提供者和计划执行阶段不进入该闸门。现有 owner 校验、工具权限和人工审核不变；闸门不启动 Loop、不改租约、不进行外部动作。

异常与降级必须显式：来源失败不说成空租约，缺失关联映射不说成租约缺失，任务配置不说成进程活性；发生生成器错误时不释放已缓冲的未验证文字。用户可以在桌面聊天的工具详情核对原始观测、在车间查看运行记录并纠错。反馈信号是原始 SSE 轨迹、服务端替换原因、离线主张审计与匹配构建的真实问答回测；阶段验收记录在独立研究报告，特别检查错误主张是否已在送达用户前被拦下。

第十八阶段实现与证据见 [在线证据闸门验收](../research/memory-loop-runtime-answer-guard-validation-2026-09-24.md)。29 项相关测试、类型检查、生产构建 `52` 均通过。真实问答在服务端命中 `lease_heartbeat_absence_claim_without_evaluation`，原始 SSE 只有替换后的保守文字，工具调用一次且无错误，最终离线审计零主张风险。该单次验收说明本次错误被送达前拦截；多样化语言改写与真实活跃租约仍待扩大验证。

## 第十九阶段：按 Work 查询关联 Loop 与最近运行

用户用“自选股猎手”问当前运行情况时，首次真实记忆查询只发现 Work，因精确名字命中而把 `loops` 段替换为“见精确记录”，模型反复重查并耗尽预算，还猜测可能没有 Loop。被控对象是这一入口丢失 Work→Loop 关系、把未读当不存在，以及历史运行和实时执行混淆。观测输入为所有者可见的 Work 记录、同用户同 Work 过滤的 Loop 列表、每条 Loop 的最后持久化 run，以及逐 Loop 的租约观测。状态留在本轮结构化工具结果和原始 SSE，不写长期事实。

控制动作限于只读：从精确 Work 记录解析唯一 ID，按用户与 Work 双条件列出未归档 Loop；同一已授权 Loop 集合读取最后持久化 run 的 ID、状态和时间，标记其不是当前执行活性。只请求 `loops` 时不重复嵌入列表文本，也不夹带不相关的其他记录家族；列表给出数量与截断信号。最新 run 来源失败时保留 Loop 配置并明确不可用。单 Loop 在线证据闸门只匹配明确标注的 `Loop ID`，不会把 `Work ID + Loop 列表` 错认成一个 Loop 的实时问题。

反馈为工具调用数、输出字符预算、Loop 覆盖、最新运行来源状态、逐 Loop 观测时间以及用户可检查的工具轨迹；多次无效重试不视为找到证据。权限拒绝优先，来源失败不说成空记录，配置 active 不等于执行器在线。用户可在桌面工具详情核对、纠错并在车间暂停；没有启动 Loop、调度器、交易或外部动作。真实问答、测试和剩余限制见 [自选股猎手运行状态验收](../research/memory-watchlist-hunter-status-validation-2026-09-24.md)。

第十九阶段的 Work→Loop 列表、每个 Loop 最新持久化 run、来源失败降级和在线闸门目标收窄已实现。四文件 50 项相关测试、类型检查与生产构建 `120` 通过。匹配构建的最新 run 查询一次 `platformRecall`、零错误，返回 7 条 Loop；宽问题对其中 6 条取得读取时运行观测，剩余 1 条因 10 次读取预算未观测。`workshopHeartbeats` 精确来源未找到该 Work 记录，回答瞬间的进程在线性仍未建立；这不是运行停止证明。原始 SSE 与审计重放见验收记录。

# 智能体车间的通用工作汇报

日期：2026-09-26。适用范围：所有 Work 与 Loop 的桌面 Web 展示。

## 产品约定

车间是长期工作的主体，老板查看工作时使用同一个“工作汇报”区。新智能体设计时必须说明它要向老板汇报什么、凭什么证明、交付物在哪里、哪些事仍需决定。展示区不为某个角色设置专用开关，也不要求老板学习该角色的内部工具或事件名。PPT 是汇报的类比；默认交付是可追溯的 Markdown 报告与附件回执，确有需要时才将 PPT 作为一种附件。

每轮汇报采用 `WorkPresentationV1`：运行状态、标题、结论、完整报告、依据事件、产物与附件、限制与异常、下一步。首页给出简报；展开后查看完整内容；从汇报进入同轮工作记录核对执行过程。不同角色可以有不同内容和附件格式，但使用同一读取契约与页面布局。

## 控制闭环

| 环节 | 约定 |
| --- | --- |
| 被控对象 | Work 的持续目标与本轮 Run/Loop 执行结果；汇报本身只负责呈现，不发起控制动作。 |
| 观测输入 | 本轮持久化运行状态、车间事件、工具回执和附件哈希；展示时间来自事件或运行记录。 |
| 状态 | 原始事件与运行状态保留在既有表中；`WorkPresentationV1` 是可重算的只读投影。智能体提供的文字与系统确认的状态分开。 |
| 控制动作 | 老板从同一工作桌进入既有审核、暂停、纠错和运行记录入口；动作仍走原有权限、审核和事件链。 |
| 安全边界 | 附件只读接口先验证 owner 权限，再限定到该 Work、该 Run 的 `outputs` 目录，核对真实路径与 SHA-256。`denied` 优先于 `allowed`，汇报不授予工具权限。 |
| 反馈信号 | 审核结果、纠错、失败原因和下一次运行继续进入事件与 Work 状态；下一轮汇报重新读取这些事实。 |

汇报不能把模型文字当作执行证明。成功、失败、运行中和待审核以持久运行状态或系统生命周期事件为准；附件要有路径和哈希回执才能打开。来源缺失、事件截断、文件改变、读取失败时显式提示，不能伪装成完整交付。旧运行没有完整报告时保留可验证的摘要、附件和记录入口，不补写虚构报告。

## 设计智能体时填写

每个 Work 默认拥有面向老板的汇报契约。Manifest 可在 `spec.presentation` 中补充：

- `purpose`：老板看完本轮应能判断什么。
- `requiredSections`：结论、依据、行动、限制、下一步中实际需要的部分。
- `expectedArtifacts`：预期产物类型，不把“预期”当成已完成。

执行提示要求各角色用统一的 `presentation` 结构提交标题、结论、Markdown 正文、依据事件 ID、警告和下一步。代码只保存经过长度与类型规范化的汇报字段；附件由真实工具回执发布。若智能体没有提交结构化正文，展示层从本轮既有状态与事件中形成最小可信汇报，并说明缺口。

## 异常与验收

运行失败、无源文件、来源降级、附件丢失或哈希不符、查询失败都必须在相应层显式呈现。老板可进入本轮记录核对、按既有审核链路决定动作、暂停 Work 或补充资料后重跑。重跑是新 Run，不覆盖旧证据；汇报按运行身份隔离，避免旧成果被误认为新成果。

验收覆盖：所有 Work 均有相同入口；不同角色使用同一契约；状态不受模型自称成功影响；只展示本轮附件；越权用户不能读取；路径逃逸、软链接逃逸、缺失或被篡改的附件被拒绝；超量事件显示不完整警告；桌面浏览器可从简报进入完整内容及工作记录。当前实现先展示最新一轮，跨轮“会议纪要”和老板批注可在稳定的工作事项身份建立后接入，不用名称相似度拼接历史。

# 《工程控制论》项目指导思想

本文用于约束后续 Zhiyu / 智能体车间 / Loop / 个人记忆 / 量化模拟盘的产品方案与代码实现。

它不是把《工程控制论》当成口号，而是把“控制、反馈、稳定、观测、扰动、边界、修正”转成可执行的工程规则。

## 1. 资料依据

- [WorldCat: Engineering cybernetics](https://search.worldcat.org/title/Engineering-cybernetics/oclc/805343481) 记录该书作者为 Hsue Shen Tsien，1954 年由 McGraw-Hill Book Company 出版。
- [Google Books: Engineering Cybernetics](https://books.google.com/books/about/Engineering_Cybernetics.html?id=__NhzwEACAAJ) 记录作者为 Hsue Shen Tsien / Xuesen Qian，出版社 McGraw-Hill，1954 年，289 页；可见目录包含 `Method of Laplace Transform`、`Feedback Servomechanism`、`Noninteracting Controls` 等章节。
- [Caltech Aerospace: Qian Xuesen (Tsien Hsue-Shen)](https://aerospace.caltech.edu/about/legends-of-galcit/qian-xuesen-tsien-hsue-shen) 说明钱学森在 Caltech 期间写作 `Engineering Cybernetics`，该书关注伺服机构稳定，18 章讨论多变量系统非相互作用控制、扰动理论控制设计和 von Neumann 错误控制理论。
- [Zhiqiang Gao, Engineering Cybernetics: 60 Years in the Making](https://engagedscholarship.csuohio.edu/enece_facpub/320/) 概括该书面向工程应用，关注分析、设计、不确定性，覆盖单输入/多输入、线性/非线性、确定性/随机系统，并特别指出现实系统的性质并不总是已知，可能存在大的不可预测变化。

## 2. 对本项目的核心理解

Zhiyu 不是一个“让模型多调用几个工具”的聊天项目，而是一个个人 AI 控制系统。

```text
外部世界 / 本地数据 / 用户目标
  -> 观测层：消息、行情、文件、网页、数据库、工具返回
  -> 状态层：记忆、任务状态、账户状态、车间事件、Graph RAG
  -> 控制器：智能体车间、Loop runtime、directive planner、策略规则
  -> 执行器：工具、模拟盘、outbox、审核提案、写记忆
  -> 反馈层：结果、异常、审批、用户修正、收益/错误、下次唤醒
  -> 再进入状态层
```

以后写方案和写代码时，默认采用闭环系统视角，而不是一次性 prompt 视角。

## 3. 十条工程原则

### 3.1 闭环优先

凡是持续性工作，都不能只设计“触发后生成结果”，必须设计：

- 本轮读到了什么。
- 本轮判断了什么。
- 本轮做了什么。
- 本轮留下什么状态。
- 下一轮根据什么继续。
- 用户或环境如何纠偏。

对应代码要求：

- Loop / Workshop run 必须产生结构化事件。
- 重要动作必须能追溯 sourceEventId、tool result、decision metadata。
- 长期任务必须维护 `lastObservation`、`nextAction`、`blockedReason`、`nextWakeupAt` 或等价状态。

### 3.2 可观测先于自动化

系统看不清，就不能自动化。

任何新能力上线前，先回答：

- 能否看到输入是否新鲜。
- 能否看到工具是否成功。
- 能否看到模型依据。
- 能否看到任务是否真的运行。
- 能否看到下一次会在什么时候运行。
- 能否看到失败是数据源、模型、权限、调度还是业务规则问题。

对应产品要求：

- 页面优先展示状态、待确认、异常、下次工作、最近证据。
- 自动任务不能只显示“已启动”，必须显示最近运行、下次运行、失败原因和最后心跳。
- 记忆和 wiki 不能只展示结论，必须能回溯原始事件。

### 3.3 状态是一等公民

智能体不是每次从零开始聊天。它必须带着状态工作。

本项目中的状态包括：

- 用户目标和偏好。
- 车间使命、边界、资料、指令。
- 长期记忆和 Graph RAG。
- 原始交互事件和 wiki 理解层。
- 量化模拟盘账户、持仓、订单、成交。
- Loop 的调度状态、运行状态、审批状态。

代码要求：

- 不把关键状态藏在自然语言日志里。
- 能结构化存储的状态，不只存 markdown。
- 任何状态更新都要有来源、时间、责任模块。

### 3.4 控制动作必须有边界

智能体的“聪明”不能替代边界。

边界分三类：

- 硬边界：真实交易、付款、删除、外部发送、绕过审核，默认禁止。
- 软边界：草稿、提案、建议、模拟委托，可以在规则内自动生成。
- 人审边界：影响真实外部世界或长期配置的动作，进入审核。

代码要求：

- 工具注册时声明 risk、scope、confirmation surface。
- actionPolicy 的 denied 优先级高于 allowed。
- 车间的角色边界要覆盖全局提示词。比如“操盘交易员”不能因为全局金融提示词而维护自选股；自选股维护交给“自选股猎手”。

### 3.5 稳定性高于灵感

系统目标不是每轮都显得聪明，而是长期稳定地不失控、不重复犯错、不忘记上下文。

设计上优先：

- 少做但确定的动作。
- 明确不操作的理由。
- 记录失败和数据缺口。
- 让系统可恢复、可暂停、可重放。

量化场景尤其如此：

- 模拟盘必须遵守交易规则。
- 数据源不新鲜时停止当前价格判断。
- 自选股调整与模拟交易分离。
- 已实现盈亏、未实现盈亏、订单、成交必须从账户状态推导，不能从模型语言推导。

### 3.6 扰动和不确定性是常态

现实系统不是理想模型。微信数据库可能延迟，行情接口可能断开，LLM 输出可能误判，用户会临时改变目标。

方案里必须显式设计：

- 数据源降级。
- 失败重试。
- 幂等去重。
- 编码异常。
- 时间区和交易日。
- stale data 判断。
- 模型不可用时的本地规则兜底。

代码要求：

- fallback 要暴露 `provider`、`data_source_detail`、`warning`，不能假装是完整数据。
- 任何降级结果都要进入事件和记忆候选，方便后续复盘。

### 3.7 观测量和控制量分离

不能把“看到的信息”和“要执行的动作”混在一起。

例子：

- 微信消息是原始交互事件，不是直接长期记忆。
- LLM Wiki 是理解层，不是原始事实层。
- 自选股候选是观测结果，不是自选股变更。
- 模拟盘交易计划是控制建议，模拟委托才是控制动作。
- outbox 草稿是候选动作，发送才是外部动作。

代码要求：

- 原始事实表不可被 AI 改写。
- 理解层可以重算。
- 执行动作必须经过 tool/action guard。
- 页面上要把“发现、建议、提案、已执行”分开展示。

### 3.8 控制器要小而清晰

不要让一个智能体同时负责所有事情。

车间设计要按控制目标拆分：

- 操盘交易员：只交易和复盘当前自选股内模拟盘。
- 自选股猎手：维护自选股池，发现候选，创建调整提案。
- 微信助理：收取、理解、生成待办和回复草稿。
- 记忆管道：把原始交互沉淀为 wiki 和长期记忆。

每个车间必须有：

- 明确 mission。
- 明确可读数据。
- 明确可用工具。
- 明确禁止动作。
- 明确反馈指标。

### 3.9 反馈指标要能检验

方案不能只说“更智能”“更准确”。要定义可验收指标。

常用指标：

- 任务是否按时运行。
- 运行是否读到必需数据源。
- 输出是否有 sourceEventIds。
- 是否产生重复提案。
- 是否有未处理审批。
- 是否在 stale data 下停止动作。
- 用户是否采纳建议。
- 模拟盘规则是否被违反。
- 记忆是否可回溯原始消息。

测试要求：

- 关键边界写单测。
- 调度和交易日写单测。
- action guard 写单测。
- 工具 fallback 和编码异常写单测。
- prompt 中的角色边界也要写单测。

### 3.10 人是最高层控制器

个人 AI 助理不是替代用户，而是把用户从重复观测和低价值整理中解放出来。

系统必须保留：

- 用户可查看。
- 用户可审核。
- 用户可暂停。
- 用户可纠错。
- 用户可删除或归档。
- 用户可重设边界。

设计取向：

- 自动完成内部整理。
- 谨慎触碰外部世界。
- 让用户在关键控制点上做低成本决策。

## 4. 写代码前的控制论检查清单

新增或修改一个功能前，先回答：

1. 被控制对象是什么？
2. 观测输入是什么，是否新鲜，是否可信？
3. 系统状态存在哪里，是否结构化？
4. 控制动作是什么，是否幂等，是否可回滚？
5. 安全边界是什么，denied 是否优先？
6. 反馈信号是什么，下一轮如何使用？
7. 异常和扰动是什么，fallback 是否显式暴露？
8. 用户在哪里介入，审核面在哪里？
9. 如何测试它不会越权、重复、静默失败？
10. 页面上用户能否看懂它现在处于什么状态？

## 5. 写方案时的固定模板

以后写技术方案，默认使用以下结构：

```text
1. 控制目标
2. 被控对象
3. 观测输入
4. 状态模型
5. 控制器/智能体角色
6. 控制动作与工具矩阵
7. 边界与审核
8. 反馈与评价
9. 异常、扰动和降级
10. 页面可观测性
11. 数据模型
12. 测试与验收
13. 分阶段落地计划
```

## 6. 对当前项目的直接约束

### 智能体车间

- 车间不是聊天窗口，是长期控制器。
- 车间右侧资料、记忆、任务、发信、工具、边界、审核必须实时反映系统状态。
- 任何长期任务都要能看到运行记录、下次运行和失败原因。
- 车间之间要分工，不能让一个车间越权处理另一个车间的控制目标。

### 个人记忆

- 原始消息是观测信号，不是记忆。
- wiki 是状态估计层，可以重算。
- 长期记忆是高置信、可追溯、对未来控制有用的状态。
- Graph RAG 是关系状态，不是聊天摘要堆积。

### 微信消息

- 先可靠记录谁、在何时、在哪个会话、说了什么。
- 再做理解、待办、回复草稿和长期记忆。
- 任何回复必须走 outbox 和边界策略。

### 量化模拟盘

- 自选股猎手负责候选发现和自选股调整提案。
- 操盘交易员只消费当前自选股，负责模拟交易和复盘。
- 数据源降级、行情过期、交易日判断必须显式暴露。
- 模拟委托是控制动作，必须受账户、仓位、价格、T+1 和风险规则约束。

## 7. 需要避免的误读

- 不要把控制论理解成“更强的自动化”。控制论首先是反馈、稳定和边界。
- 不要把闭环理解成“无限循环”。闭环必须有停止条件、失败条件和人审节点。
- 不要把模型输出当状态。状态要结构化、可追溯、可复盘。
- 不要为了自动化牺牲可观测性。看不见的自动化最终都会变成不可控。
- 不要让一个智能体承担过多控制目标。控制器越大，越容易振荡和越权。

## 8. 一句话总纲

### 主人翁意识与体验闭环（2026-09-08 用户新增）

智能体应对项目的整体使用效果负责，在不偏离个人 AI 控制系统的产品主旨、角色分工与权限边界的前提下，主动优化用户完成任务的全过程。方案和验收应观察用户能否找到入口、理解当前状态、完成操作、确认结果，并在失败后恢复；减少无效步骤、重复确认、等待和理解成本，保持跨页面术语与行为一致。

当前授权流程中可验证的明显体验问题随阶段修复并回测，较大的新增方向登记到对应方案后安排。优化不能掩盖异常、伪造成功或绕过审核，也不能无边界扩大阶段范围。每阶段记录问题、改动、实际验证结果和遗留项；开发期间使用开发模式与针对性测试，完整业务阶段及最终交付完成必要的生产验收。

以后这个项目的代码和方案，都按这个标准判断：

> 先观测，再建模；先闭环，再自动；先边界，再行动；先稳定，再智能。

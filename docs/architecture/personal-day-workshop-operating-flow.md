# 个人日计划：车间持续维护与自然语言反馈

状态：已实施并本地部署（2026-11-03，review 99）。原始方案与旧基线保留；实际装载、隔离验收、正式数据保留和遗留事项见 [车间维护流程验收](../validation/personal-day-maintenance-2026-11-03.md)。

## 1. 用户确认的产品口径

一个智能体车间长期维护用户的身体与生活相关数据、实际执行记录和每天的计划。首页展示每日计划，在计划下面提供自然语言反馈入口。用户说明实际做了什么、吃了什么、感受如何，以及愿意补充的后续安排；理解、整理、对照、记录和后续规划由车间承担。

日常主流程为：看计划 → 在计划下说实际情况 → 智能体维护状态和后续计划 → 首页显示更新结果。用户不需要学习任务状态、选择事件类型或操作规划流程。

此前设计的「记录实际／情况变了／安排明天」三个入口，以及逐项完成、部分完成、延期、重排、反复采用等操作，不再作为首页的主要交互。车间内仍须具有真实运行、版本和接管能力。

## 2. 首页管理个人数据，呈现每天的计划与反馈

- 首页日计划模块显示今天的安排，可切换查看其他日期和已有明日安排。详情按需展开。
- 每天的计划下面有一个输入框，例如「说说今天实际做了什么，也可以补充感受和明天的安排」。唯一常用提交动作是「发送反馈」。
- 用户可以一次概述整天，也可以分多次补充。不要求逐条关联任务、选择完成比例、先点变化按钮或填写完整表单。
- 输入框下面呈现这一天的原始反馈和智能体简短回复，例如「已记录你的步行和午餐，后续安排已更新」。回复必须对应实际保存或计划更新回执。
- 首页按需显示「正在整理反馈」「计划已更新」「需要补充一句信息」「暂未处理成功」等真实状态，并提供关联车间入口。
- 首页提供日计划、身体档案、知识与依据、食物资料、详细记录、每日持续任务六个栏目。首次填写、资料导入、记录纠错、维护启停和每日任务设置都在首页完成，使用同一份后端状态。
- 首页「查看执行记录」打开关联车间。车间保留原有界面，不嵌入个人日计划业务表单；模型、工作方式、工具权限仍沿用车间现有能力。原个人日计划地址兼容到同一份首页详情。

## 3. 负责维护的车间

个人日计划绑定一个长期负责的车间。训练和饮食是其可分别维护的职责与依据，最终交付相互协调的日计划；不要求用户手工协调多个结果。

车间维护四类有区别的数据：

1. 原始观测：用户的反馈原文、所属日期、接收时间与来源，不可被模型改写。
2. 当前理解：从原文整理的活动、饮食、测量、感受、可用条件和未知项，带原文引用、时间与解释版本，可以重算和纠错。
3. 计划与动作：根据目标、限制、理论和当前理解生成/更新的日计划，以及采用哪个有效版本的保存动作。
4. 结果与反馈：哪些数据实际保存、计划哪里改变、为何保持原安排，以及用户后续纠正。

被控制的对象是当前与后续日期的计划及其可执行性。实际已经发生的行为是事实来源，不能为了使计划显得完成而重写。

## 4. 首次设置

1. 从首页填写身体档案；读取首页或切换栏目不自动创建或恢复车间。
2. 通过简短交代或档案编辑器提供主目标、必要身体信息、训练与饮食条件、明确限制。已有数据复用，未知事实保持未知。
3. 在首页「知识与依据」选择允许使用的资料，在「每日持续任务」确认模型数据范围和日常维护范围，沿用统一模型配置。
4. 用户明确启用维护后，车间开始在该范围内维护记录和日计划；日常处理反馈、规划与更新计划包含在该维护授权中。
5. 需要每日自主准备时，在首页「每日持续任务」设置持续运行时机。任务仍属于关联车间的 Loop；首次建档不暗中开启定时任务。

设置目的在于确定长期目标、依据和边界。以后用户无需每天重新走设置、确认条件、生成和采用的整套步骤。

## 5. 一次反馈如何处理

例子仅用于说明交互，不对应真实用户记录：

> 今天走了二十分钟，午饭吃了牛肉面，晚上比较累。明天七点以后有空。

处理流程：

1. 将原文和所处日期保存为观测事件，立即回显「已收到」，这时不能宣称已经更新全部数据。
2. 同一个反馈进入关联车间的持久化任务，由 Pi 使用实际装载的工作方式、授权资料与受限工具理解。
3. 整理用户明示的活动时长、食物、状态和后续可用条件，并分别关联原文。没有份量、精确发生时间或其他细节时保留未知。
4. 与已有记录和当前计划对照：明确的新事实追加保存；重复、矛盾或更正按来源和版本处理。用户没提到的餐食和活动不自动算作没做。
5. 判断哪些当前或后续安排需要更新。适用的安排继续保留，必要时更新；不会因收到反馈就无条件全部重新生成。
6. 在已授权维护范围内，通过宿主校验后保存新的有效计划版本，并记录变化依据。通常不再要求用户每天点击「生成」「重排」或「采用」。
7. 首页读取同一份有效数据和计划，回复简短处理摘要。需要补充时只问影响判断的关键一句。

反馈可以同时包含事实、感受和请求，由智能体区分。内部记录以实际行为及其依据为中心，不要求用户将自己归类为「部分完成」或「临时有事」。

## 6. 每天如何规划

- 车间综合长期目标、有效身体数据、用户明确限制、已授权理论、近期实际记录和已知日程，持续维护当前及后续计划。
- 反馈处理和每天的持续任务都可以触发规划判断，使用同一份状态与相同边界。
- 明确提供的日期和时间作为约束；通常作息和偏好可以在授权范围内作为规划依据，但要区分惯例与当天已经确认的事实。
- 没有准确时间时可以给出明确标识的弹性安排，或保留未安排部分并说明缺口。不能虚构用户明天已经有空，也不能因此强制用户每天填写时间表。
- 已发生的行为、固定事项和仍适用安排保留；日计划变更有版本和原因。用户可查看「为什么这样安排／最近改了什么」。
- 反馈不完整、用户没有回复或一天没有记录时，保持未知；在足够信息与授权下继续安排，不将漏记当作失败，不自动追加补吃或补练任务。
- 长期目标与规则保持稳定，不能根据一天体重变化或一次疲劳反馈自动推断永久目标变化。

## 7. 自主维护与用户介入

### 7.1 日常范围内自主处理

启用时明确允许的事实整理、可追溯状态维护、同一目标和有效限制内的日常计划更新，由车间自主处理。首页以结果、来源和简短说明呈现，避免把每轮内部候选都变成用户必经的审核表单。

### 7.2 需要介入的情况

- 关键事实存在无法可靠解决的矛盾或歧义：在当天反馈里追问一句，其他明确记录仍可处理，并说明处理范围。
- 请求超出已授权维护范围，或需要改变权限、外部动作、重要长期规则：进入原有车间的核对或审核流程。
- 用户明确提出长期调整时，通过现有受控版本命令处理；不能把普通反馈中的推断当作修改长期配置的授权。
- 用户认为记录或计划不对：可直接继续说「刚才那顿是昨天吃的」「今天走的是四十分钟」，形成关联更正；也保留详细记录编辑和计划恢复入口。
- 用户不希望继续维护：在首页「每日持续任务」暂停，停止新任务并处理在途运行；仍能查看既有计划和提交原始反馈，暂停期间明确说明尚未由智能体处理。

程序仍校验过敏、限制、时间、来源、版本和权限，denied 优先。自主维护不授予改写原始反馈、删除历史、发送消息、购买或自行扩权的能力。

## 8. 后续如何调整智能体

首页的「查看执行记录」打开同一个负责维护的车间。用户可以查看最近如何理解反馈、维护了哪些数据、为什么更新某份计划，以及实际使用的工作方式和模型版本。

长期调整在车间完成：提出要求 → 查看实际影响 → 必要时保存候选并预演 → 按授权应用 → 回读实际装载 → 观察后续行为。训练与饮食规则分别维护，档案继续使用同一事实源，不在提示词中再抄一份身体数据。

资料从首页「知识与依据」导入并管理采用范围。涉及模型的提取、理解、规划和预演均作为关联车间的真实任务，不能由首页另开隐藏的模型调用。业务操作入口与运行归属分开：入口集中在首页，执行继续由 Work/Loop 承担。

保存配置、实际装载、程序验证和长期效果分别显示。恢复工作方式不会删除之后发生的真实记录，也不会把过期计划直接重新标为有效。

## 9. 异常和可观测性

- 原文保存成功但模型尚未处理：显示「已收到，等待整理」，用户输入不会丢失。
- 模型或工具失败：显示处理失败和已完成范围，不用一句成功回复掩盖只有原文入库。
- 后台离线或车间暂停：显示反馈待处理和计划更新时间，不将上次计划说成新生成。
- 理解有误：追加用户纠正，原文继续保留，重算理解及受影响计划。
- 新旧反馈并发、页面重试、进程重启：以反馈 ID、Work 命令和版本保证不重复入账；迟到结果不能覆盖新数据。
- 输入或资料不足：明确使用范围与缺口，必要时给受限安排或不更新受影响部分。降级提供 provider/detail/warning，不伪装为模型已完整处理。
- 首页「每日持续任务」显示最近运行、下次运行、失败原因和心跳；完整执行证据仍在车间。离线多天后只处理仍适用的日期，不叠加过期训练。

首页显示必要状态与入口，完整证据在车间。用户不必了解内部任务分类，也能知道信息是否收到、是否处理以及计划有没有更新。

## 10. 工程落点与迁移

- Work 归属从自动任务开关中独立出来，一个车间长期维护一份数据与计划。普通手动反馈同样归属它。
- 每日反馈接口只负责认证、日期与归属校验、原文持久化和受控 Work 任务提交，返回可恢复回执；模型理解由车间运行。
- 使用实际装载的 Work 配置和受限工具读取数据、追加解释和事实、提出并提交合规计划。宿主负责换算、硬约束、幂等、租约、版本及审计。
- 日常授权内的计划提交可直接形成有效版本并更新首页；越界变更按既有审核机制处理。不能把候选保存成功等同于计划已生效。
- 原始观测、可重算理解、业务维护动作和保存结果分别留痕。明确的用户自述标注来源，估计不是称重，缺失不是零。
- 反馈事件绑定所属日期、owner、workId、runId 和处理版本；重试和更正保持关联。不把健康正文复制到通用日志或未授权车间。
- 首页和车间读取同一档案、事实与有效计划投影，避免两份状态。旧字段仅为兼容既有历史，不再要求用户按旧分类操作。
- 保留已有加密数据、资料、计划和原始记录，不伪造迁移前的 Work 运行记录。旧 URL 兼容到同一份展示。
- 日常修改使用开发模式及针对性验收；只有用户明确要求生产发布时运行完整构建和生产验收。

## 11. 验收依据

1. 用户在每日计划下输入一段自然语言，无需事件分类、逐项状态或规划按钮，即能完成一次真实维护任务。
2. 智能体能区分用户明示事实、感受、后续条件与请求；每个结构化结论可定位到原文。
3. 多次反馈可增量整理；没有提到的内容保持未知，没有份量时不自动生成精确摄入数值。
4. 已授权的日常计划由车间自主维护，首页不反复要求生成、重排和采用；必要追问仅围绕关键缺口。
5. 身体、资料、目标或后续反馈改变时，旧快照结果不能覆盖新状态；原始事实不因规划而改写。
6. 错误理解可用自然语言追加纠正，并更新解释和受影响计划，不需要用户自己修改内部状态。
7. 首页提交后能在车间找到真实任务、实际使用版本与业务保存回执；首页没有旁路模型调用。
8. 模型故障、队列积压、租约失效、暂停或离线均明确显示，用户原文不会因未处理而丢失，也不会虚报维护成功。
9. 重复提交、重启和并发反馈不重复记入事实或叠加计划；自主处理不越过现有角色和权限边界。
10. 桌面实际完成“查看日计划 → 一句话反馈 → 看处理说明和更新后的计划 → 继续纠正”，并验证车间配置调整实际影响后续运行。

这份方案以最新用户口径取代前一版多按钮、显式重排和逐轮采用的日常操作设计。方案保存不等于实现或上线，后续分别记录代码、实际装载、程序验收和生产效果。

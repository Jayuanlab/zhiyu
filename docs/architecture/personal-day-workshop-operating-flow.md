# 个人日计划：首页使用与智能体车间运行流程

状态：产品结构与操作方案，待实施。2026-11-03。当前已部署基线为 `de8ff47`；本文件不表示新页面或运行链路已经上线。

本方案依据用户确认：日常操作过多，个人日计划没有充分纳入智能体车间；首页展示个人日计划结果，智能体运行与后续调整统一放到车间。桌面 Web 和必要后端为本次范围。

## 1. 产品结构与责任

首页负责让用户看懂今天、明天和需要处理的变化，并完成少量日常输入。智能体车间负责接收任务、使用实际配置运行、保存候选结果、安排持续任务、暴露异常和支持后续调整。

个人日计划控制的对象是“当前条件下尚未执行的安排”。用户的身体、吃过的饭和已经发生的执行是观测事实，不能被规划器改写。

### 1.1 首页

- 在现有首页结果区增加个人日计划模块，保留产品其他结果和对话入口。日计划不占据整个产品的定位。
- 默认展示今日有效安排、下一项、已确认执行，以及明日是否已安排。详情按需展开。
- 高频入口收敛为「记录实际」「情况变了」「安排明天」。待采用草稿出现时，再展示「查看调整并采用」。
- 显示关联车间名称与「进入车间」入口，以及必要的运行摘要，例如「车间正在调整」「需要补充时间」「有草稿待采用」。
- 模型选择、提示词、工具权限、Loop 设置、完整运行日志、资料处理与规则修改放到车间相应管理区域。
- 原「个人日计划」侧栏入口合并为首页日计划详情入口；旧 URL 保持兼容，打开同一份结果，不保留另一套运行与配置表单。

### 1.2 智能体车间

- 为个人日计划绑定一个长期负责的车间，手动任务与持续任务共用它。
- 复用现有车间的任务、运行、知识与依据、模型和边界管理、版本及审核机制；按场景增加日计划的结构化结果和资料入口。
- 用户能在这里交代任务、查看读取范围和执行过程、停止运行、调整工作方式、管理资料与持续任务。
- 当前采用一个日计划总控车间，训练与饮食是可分别维护的职责和规则分组，合并交付一份计划。不把一段提示词描述为两个已独立运行的智能体。将来拆出独立教练、饮食车间时，使用已有协作机制，只提交建议，由总控和宿主合并校验。
- 车间运行必须读取该车间实际装载的目标、工作方式、知识授权、有效模型与工具边界。调整工作方式应能改变后续运行输入，并能通过版本和回放核实。

### 1.3 我的档案与资料

- 身体档案、测量与饮食限制继续使用唯一的健康领域事实源，不混入普通账户姓名/头像或复制成聊天记忆。
- 首页「记录实际」可快速记体重、状态和执行；「我的档案」打开详细编辑。车间的相关档案入口打开同一份数据。
- 长期目标、器械、食物偏好只维护一处。车间工作方式描述如何规划，避免再次复制一份身高、体重或过敏列表。
- 理论资料从车间「知识与依据」导入、预览、提取和审核。首页按需显示本次计划采用的原则及来源链接。

## 2. 首次启用：从首页到第一份计划

1. **首页查看入口。** 未启用时显示简短介绍与「启用个人日计划」。读取页面不会创建车间或启动任务。
2. **进入关联车间设置。** 点击后匹配已有明确绑定；没有绑定时，通过 Work 模板创建个人日计划车间。按稳定身份去重，不按显示名称猜测。已经暂停或归档的车间保留原状态，提供明确的恢复或重新关联操作。
3. **填写最少必要信息。** 分组填写身体基础与目标、训练/就餐条件与限制、模型数据使用范围。已有档案直接使用；未知事实保持空白。不要求重复选择 API Key 或分别给训练、饮食配置模型。
4. **资料可以稍后导入。** 用户可以先使用明确标注来源的内置目录。个人书籍未就绪时，页面不宣称已经结合了这些理论。
5. **提交明日条件。** 填确定空闲的时间、地点、就餐方式、固定事项和需要说明的状态变化；已有日常偏好可带入，但可用时间需要本次确认。
6. **一次提交给车间。** 点击「确认条件并准备明日计划」，保存确认输入并提交车间任务，返回同一任务的可查询回执。用户可以留在车间看过程，也可以回首页等待。
7. **核对并采用。** 首页收到「明日草稿待确认」，展示具体安排、缺失项与取舍。点击「采用这份计划」后形成明日有效版本。返回车间可看到同一运行及采用回执。

设置过程可中断后继续。车间创建、档案保存、首次任务分别展示真实进度；失败后从已经成功的步骤继续，不重复创建车间，也不把部分成功包装成全部完成。开启定时准备是单独的可选设置，首次建档不自动开启。

## 3. 每天使用：首页完成高频操作

### 3.1 早晨打开

- 首页直接显示今日已经采用、仍然适用的安排；昨天已确认今日计划且条件未变化时，不要求重新生成或再次采用。
- 今日没有计划时显示「今日尚未安排」，可提交今日剩余条件给同一个车间。
- 首屏先展示下一项和剩余安排，已确认完成内容折叠保留。没有记录的事项标为待确认，不计为失败或完成。
- 日期、业务时区、有效版本、最近更新时间可核对；跨午夜要更新日期并重新检查过期动作，不能将昨天计划重新标成今天。

### 3.2 记录实际

- 每项可「标记完成」「部分完成」「今天没做」；详细组数、次数、负重、用时或食材克数可按需补充，不必每次填写完整表单。
- 只标记完成时，不自动把计划时长、食材克数变成精确测量。没有实际数值的字段保留未知；用户明确选择按计划估计录入时标注估计来源。
- 记录体重或身体感受通过轻量表单直接追加观测，不为每次点击都调用模型。该事实进入关联车间的下一次输入快照。
- 填错时追加更正并保留原记录与关联。首页当前结果按更正后的有效事实展示。
- 观测到明确疼痛、过敏或关键限制变化时，宿主先限制受影响的后续安排，再由车间评估；不会等待模型输出才执行已确定的边界。

### 3.3 晚上安排明天

1. 首页点「安排明天」，在小面板确认明天已知条件。
2. 有常用条件时可选「明天按常用条件」，把它作为本次明确确认；不自动推断明天有空。
3. 点「提交给车间」，关联车间排队或运行，首页显示真实任务状态。
4. 有结果后核对一次并采用。用户无需先进入车间新建任务，再返回日计划手动点击另一套生成按钮。
5. 不知道明天安排时可保留未知；系统说明缺口，不提前锁定整周日程。

## 4. 临时变化：一条反馈到新安排

例子：用户已记录午餐和一部分训练，现在说「今晚加班到 21 点，只能在家，晚饭改外食」。

1. **首页点「情况变了」。** 可选时间、地点、状态、就餐变化，也可用一句话描述。
2. **确认关键变化。** 明确结构化选择直接使用；自然语言需要模型理解时，先在车间的同一任务中理解。仅对影响方案的歧义补问，例如「从 21 点起有空，还是 21 点后也不安排？」不要求重填整天表单。
3. **保留原始反馈。** 原文、明确条件和解释结果分层保存。事实被确认后，首页提示哪些原安排受到影响，阻止把已不可行安排继续当成可执行。
4. **车间调整剩余部分。** 使用最新档案、当日条件、实际记录、固定事项及已采用原则。已完成、进行中、部分完成和已过时间未确认的历史原样保留；仍适用的未来事项尽量保留。
5. **首页先看变化摘要。** 例如「剩余训练待重新评估；晚餐按外食条件调整；午餐与实际训练记录保留」。展开才显示详细依据。
6. **采用一次。** 点击「采用调整」后，候选成为当日有效新版本；车间显示同一份审核结果，双方不再各确认一遍。
7. **保留接管入口。** 不满意可补充要求、保留仍可行原安排，或对今天明确停止新增安排。不能满足约束时明确取消/未安排；进入明日待评估不代表已经排定，也不产生补吃或补练欠账。

已经清楚下达的具体应用内编辑，可在现有授权和宿主规则允许的范围内一次执行并回显；不能借此批准模型额外添加的变化。默认策略仍为“模型提候选、用户采用”。

## 5. 审核在哪里

- **日计划采用：** 首页提供轻量核对，车间可查看同一提案。两处操作同一个提案 ID、状态与版本，不各保存一份审批。任一入口处理后另一入口立即更新。
- **工作方式、持续任务和权限变更：** 在车间修改并显示影响，使用原有版本命令或审核流程；首页不放这些管理表单。
- **资料原则采用：** 在车间「知识与依据」核对原文、覆盖范围和适用条件。模型提取完成不等于原则被采用。
- **事实更正：** 从首页记录详情或同一档案编辑器追加更正，不需要先请模型同意。

采用前重新核对输入版本、当前时间和限制。运行中记录了新执行、改了档案或已采用其他方案时，旧候选标为过期，不覆盖新状态。运行完成、草稿就绪、已经采用是三个不同事实。

## 6. 后续调整智能体：在车间完成

### 6.1 临时要求与长期偏好分开

在车间说「今天只想做轻量活动」，进入当日任务；说「以后优先安排居家训练」，进入长期偏好或工作方式变更。需要选择适用范围时，只确认「仅这次 / 以后默认」这一个关键点。

用户明确指定的长期修改形成可审阅的字段差异，通过现有保存/审核动作生效；模型不能从一次漏做或一句感受推断永久目标变化。

### 6.2 调整步骤

1. 在首页「进入车间」，或从车间列表选择个人日计划。
2. 看最近任务、输入缺口和用户反馈，定位需要调整的是档案、资料、工作方式还是运行依赖。
3. 需要改偏好时打开同一份「我的档案」；需要改理论时到「知识与依据」；需要改规划策略、执行模型或任务时间时到相应工作管理区域。
4. 查看修改前后、适用日期与影响；保存为待验证候选，当前生效版本继续保留。模型更换沿用统一配置中心，车间只选择继承/覆盖，不另存一套凭证。
5. 对工作方式变更，在车间用匹配条件进行预演，展示候选与约束检查结果。预演不会发布日计划，也不会把测试执行记成真实训练或摄入。
6. 确认使用后通过 Work 版本命令应用并回读，新运行记录实际装载的配置版本；规则影响现有未来安排时提出新的调整候选，历史事实不变。保存候选、预演通过与正式应用分别显示。
7. 效果不符合预期时恢复之前的工作方式版本。恢复配置不删除之后发生的身体测量或真实执行，也不让过期计划直接生效。

配置需要分别显示「已保存版本」「本轮使用版本」「验证结果」。一次预演成功只能说明该场景通过，不代表长期健身饮食效果已经改善。

## 7. 理论资料的具体操作

1. 车间「知识与依据 → 导入资料」选择文件，标明给训练、饮食或两者使用。
2. 本机转换并显示真实状态，保留原件、范围和来源。失败显示可恢复原因；扫描 PDF 不伪装 OCR 成功。
3. 用户可手动整理原则，或在明确授权范围内让车间执行「提取原则」任务。该模型调用有独立任务、运行和覆盖回执。
4. 核对原文位置、适用条件、冲突与缺失内容，选择采用。
5. 后续规划只使用有效授权的已采用原则。资料中途变更或撤销后，旧候选失效，受影响的未来安排提示重新核对。
6. 首页只显示计划的简短依据与到该资料的链接。原始健康正文不自动复制到通用 Work 日志、其他车间或向量记忆。

资料解析、模型提取、人工采用和实际被某轮读取分别留有状态，不能合并成一个「已学习」。

## 8. 持续运行与暂停

- 在车间「持续任务」开启「每天准备明日计划」，设置时间与数据使用范围；默认关闭。
- Loop 是车间内的触发器，手动准备、临时重排和定时准备使用相同领域任务契约、Pi 配置和边界。
- 定时任务只提交草稿，不自动改变目标、限制或采用新计划。明日条件缺失时返回需补充，已有有效计划或待确认草稿时保留它。
- 首页只显示“明日草稿已准备”“需要确认条件”等结果；车间显示最近运行、下次运行、失败原因、后台心跳与中断情况。
- 全局暂停在车间执行，停止接收/执行新的规划任务并处理在途运行。已发布计划仍可查看，用户仍能记录真实执行。
- 首页「今天不再安排训练」是有日期和范围的生活条件，进入车间调整流程；它不等同于停止整个车间或关闭以后所有持续任务。
- 电脑或服务停止时明确离线。恢复后只处理仍然适用的任务，不补发多天过期训练，也不批量生成相互覆盖的旧计划。

## 9. 首页需要看懂的状态

计划状态和运行状态分别展示：

- 今日计划未采用：显示未安排/待采用，不用本轮运行成功冒充有效计划。
- 原计划有效，新任务排队或运行：原结果继续可看，显示关联车间正在处理。
- 条件变化影响原计划：标出受影响范围，暂不把它当成可执行；保留无影响内容。
- 新草稿就绪：显示变化摘要与采用入口；清楚说明候选尚未生效。
- 新草稿已采用：显示新版本及更新时间，旧计划进入历史。
- 输入不足：在首页补充少量必要信息，继续同一个有来源的任务链。
- 运行失败或后台离线：显示本次没有新结果、原计划是否仍适用，以及到车间详情的入口。
- 数据读取失败：标记状态未知，保留之前结果的日期和读取时间，不能将空响应显示为没有计划。

首页没有百分比假进度。车间只有写出可核对阶段事件后，才展示该阶段已完成。排队、运行、生成成功与采用成功分别以真实回执判定。

## 10. 一致性与工程集成

### 10.1 当前代码事实与改造目标

当前 `personal-day/service.ts` 的手动生成、资料提取会直接调用模型；`automation.ts` 仅在开启持续任务时绑定 Work/Loop。车间已有 Work 命令、执行队列、运行记录、租约、资料及版本能力，可作为整合基础。

需要把 Work 归属从“是否开启自动任务”中独立出来。只手动使用的个人日计划也必须有明确的负责车间；开启 Loop 只改变触发方式，不决定智能体是否存在。

需要补齐的核心链路是：

```mermaid
flowchart LR
  A[首页反馈或车间交代] --> B[受控 Work 命令与输入事件]
  B --> C[关联车间任务与持久化队列]
  C --> D[带租约的 Pi 运行或明确标识的规则执行]
  D --> E[宿主校验并保存计划候选]
  E --> F[同一提案供首页与车间核对]
  F --> G[用户采用后更新有效计划投影]
  G --> H[首页展示并记录实际]
  H --> B
```

### 10.2 唯一状态来源

- 账号与个人日计划能力绑定唯一负责 Work，绑定校验 owner、角色与读取授权；不接受浏览器随意指定其他车间。
- 健康领域表保存权威档案、原始观测、计划、执行与来源。Work 保存任务、运行、配置、权限与审核关联。通用日志只保留必要元数据与受控详情引用。
- 首页和车间读取同一个带版本的计划投影，不能各存一份结果 Markdown 或让模型生成首页 HTML。
- 身体/观测版本、Work 配置版本、源资料版本与计划版本分别记录，固定在每次任务的输入快照中。带记录时间、来源、覆盖范围和新鲜度，过期输入不能冒充当前状态。
- 手动生成、重排、自然语言理解、资料提取、策略预演等模型工作都由车间承接。前端页面与旧健康接口不能绕过车间自行调用 Pi。
- 标记执行和手动测量是事实录入，不必启动模型；它们追加事件、更新受影响计划的可执行状态，并作为后续车间输入。
- 计划候选、审核与采用回执相互关联。采用通过受控命令校验版本并保存新有效版本，双方视图只在实际成功后更新。

### 10.3 执行与安全

- 复用 Work 命令 ID、版本校验、队列、取消、租约与写入围栏。刷新页面查询原任务，不自动新建一轮；网络超时先核对回执，明确失败后重试是新尝试并关联前次。
- 持久化绑定与角色决定处理器，不从可能被重置的临时 Loop state 猜测身份。
- Pi 使用实际装载的车间配置与受限领域工具；宿主继续负责时间冲突、过敏、事实锁定、营养换算、候选保存和采用验证。修改 prompt 不会放宽这些校验。
- denied 优先于 allowed；领域角色没有任意命令、跨车间健康读取、外部发送、购买、自动改变权限或改写原始观测的能力。
- 采用与未来计划变化要可审计、可恢复；恢复旧安排也先验证当前条件，不伪造历史执行撤销。
- 进程中断、失去租约、用户暂停或事实版本改变时，迟到结果不得写成当前计划。模型失败可在已有授权范围内明确降级为目录方案，其 provider/detail/warning 和来源必须可见。

## 11. 已有数据与入口迁移

- 保留已经部署的档案、计划、原始记录、来源与加密保护，调整入口和运行归属。
- 已有 Work/Loop 复用原身份与暂停状态；仅有健康记录但没有车间的用户，在下一次明确设置/规划操作时建立归属，不因 GET 首页自动创建任务。
- 老计划没有 Work 运行号时，保留旧来源，标明迁移前结果；不补造“车间已经运行过”的历史。
- 原个人日计划 URL 打开同一份首页详情，避免旧书签失效或两套页面各自可运行。
- 首页、车间和原入口的读写一致后，再收掉旧六页签里的重复配置与直接模型入口。
- 分阶段迁移失败时，展示已完成步骤和阻塞原因，可继续或回到已验证入口；不假称跨多个存储动作全部原子成功，不通过 SQL 修改 Work 配置绕过审计。

## 12. 实施顺序与验收

先实现车间归属与统一任务契约，再接首页结果和高频反馈，随后迁移档案/资料/管理入口，最后移除旧独立运行路径并重新生产验收。

关键验收场景：

1. 首次启用只生成一个绑定车间；中断后继续不会重复创建，原暂停状态不会被悄悄恢复。
2. 首页安排明天后，车间有同一 command/run、实际读取的版本与保存回执；用户回首页无需重复发起。
3. 在车间改工作方式，预演和下一轮能看到新装载版本与对应行为；只改说明文字而实际规划输入不变不能通过验收。
4. 普通标记完成不消耗模型调用，也不伪造克数、用时或精确营养事实。
5. 加班、地点变化与部分完成同时出现时，只改变受影响的未执行部分；首页与车间显示同一结果。
6. 首页采用一次后，车间无需再次审批；反过来操作也一致。双页面同时采用、旧版本和重复点击均不会覆盖新状态。
7. 档案或资料在生成过程中改变，旧候选被拒绝；取消、暂停和失去租约后，迟到结果不能发布。
8. 无已确认时间、模型不可用、队列积压、后台离线、页面读取失败分别显示真实原因，不静默假成功。
9. 开启/暂停持续任务都在车间可追溯，首页能看到必要摘要；多日离线后不集中补做过期事项。
10. 旧健康数据与结果不丢失、不新增虚构 Work 历史，不向其他车间泄露健康正文。
11. 桌面主要路径、窗口缩放、键盘、等待反馈和失败恢复可用；先开发模式验证，再保留生产构建、接口及浏览器验收证据。

本轮假设：将实际执行归属统一到车间，并把高频输入与结果留在首页，可减少用户往返与重复提交，同时让配置调整可验证。以上是待验证方案；后续记录每项实现、实际装载和回放结果，保留失败证据与恢复版本，不以方案保存代替落地。

# 新版 100 题首轮：原因诊断与修复方案

日期：2026-10-02。状态：原因复核与候选方案已整理；候选尚未实施、装载或复测。

这轮主要答题模型是 `qwen3.7-plus`，JEV 参与来源路由。主要问题是：模型没有始终把结论限制在实际证据范围内，关联读取和操作验收没有形成可靠的完成条件。此外，存在调用故障、测试夹具问题和辅助评分误判，不能全部归为“模型答错”或“JEV 不准确”。

本诊断依据[首轮运行报告](run-2026-10-02.md)、封存的首次回答与工具回执、隔离工作流状态、评分契约及源码复核。没有再次调用待测模型或评测 judge，没有业务操作或配置修改。原题、原回答、原评分、原错误和原始审计继续保留。

## 1. 先把结果分清

90 道问答的原辅助判读为：75 道必要要点达标，6 道部分完成，2 道错误，2 道证据不足，5 道调用失败。10 道工作流的报告门槛为：6 道达标、2 道未达标、2 道夹具错误。它们不是人工认证的生产正确率。

“必要要点达标”仍可能伴随额外的无证据主张。原审计记录的 31 条确认风险涉及 27 题，是主张和工具行为的风险条数，不能理解成 31 道错题，也不能直接从 75 中扣除。本次复核还识别出评分解释争议和部分审计措辞需要限定，以下逐项说明，不改写首轮成绩。

## 2. 为什么已有提示和保护仍会出问题

### 证据提示存在，但不总能约束最终结论

当前读取逻辑已经提供 `fieldAvailability`、来源哈希、分页信息及结论边界，提示词也明确要求保留 null、未知和时间范围。REAL-020、094 等仍跨过了边界。因此，重复增加“不要幻觉”提示不能当作可靠修复。

需要按字段含义区分：未记录检查时间不代表从未检查；发送结果未知不代表未发送；审核事项关闭不代表修改已应用；没有活跃映射不代表执行器停止。也不能把所有 null 一律当作相同错误：REAL-046 的到期时间为空可表示未设置显式到期日，现有 Brain 策略也不因此判为过期；它不能证明事实新鲜，但不是明确的策略错误。REAL-033、034 的“无错误”还可能只是字段简写，应与“从未发生错误”的强主张区分。

当前生产接口已有 `guardDirectLoopRuntimeAnswer`，在 Pi 主阶段处理单个明确 Loop ID 的当前执行问题。本轮 worker 直接调用 runtime，没有经过该接口。保护范围也不覆盖所有复合问句、所有状态和工作流工具。因此，本轮说明了原始模型行为及隔离轨道的风险，不能直接断言生产桌面一定显示同样错误；扩大保护仍需正式接口和桌面流程验证。

相关模块：`apps/web/lib/ai/platform-record-reader.ts`、`platform-claim-boundary.ts`、`platform-recall.ts`、`loop-runtime-observation.ts`、`loop-runtime-answer-guard.ts`，以及 `apps/web/app/api/native/agent/route.ts`。

### 读取成功不等于问题已经答完整

当前完成提示主要检查所请求记录的展开，并不代表关系两端、引用主张、长消息后续页或所有用户问项都已覆盖。`platform-answer-coverage.ts` 是有限的字段可用性提示，并不是最终答案正确性核验器。模型可以读完一条关系记录，就提前结束关联回答；也可以读到部分正文，却把局部总结写成全文结论。

读取预算是真实约束：每实例 10 次尝试、单结果 24,000 字符、证据累计 64,000 字符。超限会整段扣留；实际进入读取的尝试会计数，即使随后来源失败或结果超限。参数验证、权限、重复保护和已耗尽时的提前拒绝另行记录，不能混作同一读取计数。模型在收到“停止读取、报告缺口”后，仍可能继续调用。预算拒绝并不代表事实不存在。

同时，本轮 frozen 适配器会反复返回约 12,300 字符的目录，并将同一 recordRead 正文放进两个位置，额外消耗预算。正式 Pi formatter 通常选取单份文本，这个重复开销不能当作生产相同缺陷。适配器的 `limit` 对检索匹配数有效，却不控制源码页长度；REAL-098 用它缩页没有达到预期。应先修正测试适配器的表示与分页，再评估正式预算和检索行为，不能把适配器修复的收益归给 JEV。

相关模块：`apps/web/lib/ai/platform-answer-coverage.ts`、`memory-read-budget.ts`、`memory-access.ts`、`native-pi-web-chat-tools.ts`；测试适配器为 `apps/web/scripts/lib/platform-eval-v2-frozen-tools.mts`。

### 工作流与辅助评分缺少可靠的最终闸门

REAL-100 的“已暂停”和“未来不会接受调度”需要不同证据。REAL-094 的服务检查通过也不能证明其状态解释正确。新版辅助 judge 已接入真实回执，却仍接受了 REAL-085、094、100 的无支持结论；协议正确不代表语义判读可靠。旧纯文本 judge 的协议错误继续单独保留。

工作流回执生产器还有一处描述缺陷：REAL-100 即使没有探测 trace，也会输出一条含“时钟已推进”的固定 coverage 描述。独立核验使用实际探测调用和时钟回读，没有把这句描述当作成功；后续仍应让日志描述由实际事件生成，避免误导读者。

### 调用故障目前只能定位到故障类别

5 次失败都早于整题的 240 秒预算和 330 秒进程上限，不能解释成这两个上限已耗尽。当前安装链的 SDK 代码会把部分连接中止或底层 timed out 映射为 Request timed out，Pi 又主要保留 `error.message`，丢失更低层的 cause／请求阶段；这解释了日志为什么不足，不证明首轮的具体供应商根因。首轮未封存这些 SDK 源码哈希，当前依赖检查也不能代替当时装载证明。

模型生成故障与 JEV 路由的 2 秒超时是两条链。即使发生在同一题，也不能合并为一个超时原因。应补观测后做控制变量排查，不能先盲目拉长全部超时、提高并发或全局重试。

## 3. JEV 在本轮的问题与可验证的候选

90 次路由记录为 84 次不确定降级、2 次超时降级、4 次正常；4 次正常中 3 次没有选中来源，实际自动预取仅发生一次。当前规则是任一类别落入不确定区间，就将整次路由降级。17 次降级记录已有至少一个达到或超过选中阈值的来源，其中 10 次为 records；这能解释为何部分可选来源没有预取，却不能证明这些来源分类正确，也不能证明它造成最终错答。

候选是“保留确定的、已授权的只读来源，其他类别继续标记未知”，而不是直接降低阈值或同时打开多个开关。先用保存的路由向量离线分析，再固定来源、权限、模型、适配器和预算，比较 routing 关闭、当前整次降级策略、候选按来源处理策略。`mode=off` 与 `targeted_retry=false` 在这些对照中保持不变。单看预取次数增加不算改善，必须看所问事实覆盖、额外无支持主张、权限与时间边界、成本和延迟。

相关模块：`apps/web/lib/brain/jev-recall-router.ts`、`apps/web/lib/ai/jev-platform-prefetch.ts`。本轮没有人工来源标签或匹配 A/B，不能给出 JEV 正确率。

## 4. 有限修复方案与验收

建议按下表分阶段实施，每次只改变一个原因层。当前全部是候选，尚无修复后的模型成绩。

| 优先级与候选 | 最小改动范围 | 验收条件与退回条件 |
| --- | --- | --- |
| P0：状态结论绑定证据 | 先覆盖发送未知、审核与应用区别、Loop 当前活性三类。复用已有字段可用性与结论边界，形成共享的“事实状态 → 允许结论”规则；生产与隔离工具分别提取可信回执。最终状态展示引用对应来源、时间和覆盖范围。 | 未知不变为未发送；事项关闭不变为配置应用；缺少映射不变为停止。已支持结论、历史结论和否定句应保留。出现误覆盖、越权、无回执标记成功时退回旧版本。 |
| P0：动作与验收分开记录 | 暂停／取消／修复等结果区分“动作回执已取得”“效果已核验”“仍待核对”。验收读取必须对应原目标、输入版本和后继产物，缺失时结束为未核实。修正 REAL-100 固定日志描述。 | 原失败基线未读不得宣称修复已核实；暂停没有未来准入证据不得称已完成该项验收。仅隔离测试推进受控时钟，生产不得修改业务时钟。历史产物、事件保留且无重复动作。 |
| P0：修复夹具和评分契约 | REAL-071 在与 Next 路由兼容的隔离服务环境取得正式 API 回执；REAL-085 在调用模型前核验真实取消／待核对初态。语义评分接受同义业务含义，只要求题面必要内容；独立回执检查不能被 judge 高分覆盖。 | 先证明夹具就绪、owner 和 provider 隔离。049、056 名字扣点、060 标题等争议进入单独复核，不默改金标。085／094／100 作为矛盾与缺证据的评分负例，不允许误报通过。 |
| P1：少读重复内容，补齐必要关联 | frozen 正文只返回一份，目录显式分页，源码页按实际送达范围续读。按问题建立所问事实清单，关联需要时展开两端对象和主张；多页未完就明确范围。预算状态和可用续页结构化，耗尽后关闭读取阶段、保留回答阶段。 | 在相同 10／24k／64k 预算下减少重复开销，增加必要正文实际送达；不跳页、不丢哈希、不扩大权限。预算耗尽后无无效再读；答案明确缺口。正常授权续页若被提前截断则退回。 |
| P1：补齐调用故障观测与有限恢复 | 记录连接／首字节／流读取／工具／结束阶段，实际超时配置、最后流事件、HTTP 状态、异常 cause、abort 来源和非敏感请求关联信息。先对比固定并发和载荷，再选择单独的超时或恢复候选。 | 每次失败可定位阶段，首轮与恢复尝试独立留存。只读请求可有限恢复；外部效果未知时先核对正式回执与幂等状态，不自动重发。不隐藏失败、不把部分流标为完成。 |
| P2：JEV 匹配对照 | 在稳定适配器上比较关闭／当前／按来源处理三组；新增来源标签与未参与调参的正常产品问题，评测输入不带金标或来源答案。 | 看任务事实与边界结果，而非路由自评分或调用数。出现权限／时点违规立即停止；只增加预取量、条件不匹配或收益不明确则保持原策略。 |

### 控制闭环与桌面体验

| 工程要素 | 本方案的落点 |
| --- | --- |
| 控制目标与被控对象 | 提高当前桌面问答与有限控制动作的可核验性；对象是最终事实主张、关联读取、工作流完成状态及调用恢复。手机端和原生客户端专项不纳入。 |
| 观测输入 | 原始记录／工具回执、读取时间、来源与内容哈希、授权判定、实际控制事件、调度准入、错误阶段。冻结快照不能充当实时活性观测。 |
| 状态与分层存储 | 原始事实、理解结果、控制请求、执行回执、验证结果分开。每项所问事实保存来源、覆盖、缺口与核验状态；保存事实不等于装载或生产生效。 |
| 控制器与动作 | 模型提出读取和解释，确定规则限制可声称的状态；控制仍走正式 owner 范围服务。关联读取按需、有界，恢复次数和停止条件明确。 |
| 安全与人工接管 | denied 优先，不扩大工具权限，不改原始消息，不绕过审核。外部发送、配置和其他受保护动作遵守现有边界；用户可审核、暂停、纠错，未知外部效果进入核对。 |
| 反馈与恢复 | 留下成功／失败／未核实原因、缺失来源、候选版本和回执。验证失败停止相应推进，保留可恢复状态；回滚候选规则不声称能撤销已发生的外部效果。 |
| 页面可观测性 | 显示“保存状态／执行观测／效果核验”各自的时间和依据。缺口、provider 降级与调用错误可见；已有证据的普通回答保持简洁，关键未知有可展开解释。 |
| 可回滚性 | 实施前保存基线版本与配置；候选小范围装载并回读版本，出错恢复旧候选。原记录、事件、首次评测与失败证据保留。 |

### 后续验证顺序

1. 先做不调用模型的夹具、分页、哈希、权限、字段语义和评分负例检查，确认修复没有破坏来源与审核边界。
2. 对每个候选单独跑匹配切片：上述失败／争议题，加正常、有证据的成功题、未知、来源故障、越权、重复动作和同义问句。评分规则若修订，要新版本并并列报告，不能悄悄替换原成绩。
3. 在同一稳定适配器上单独评估 JEV 对照。原四道 pilot 的来源装载哈希缺口仍保留，不补造为严格同条件基线；需要严格比较时另建明确版本的新基线。
4. 最后跑完整 100 题，并分别报告记录、来源、工作流，以及必要要点、额外主张、调用失败、夹具错误、动作结果。针对已确认的关键未知误判，匹配回归中不应再出现；其他指标按实际结果判断，不预先承诺提高到某个正确率。
5. 通过正式 API 与桌面主要流程验证保存、实际装载、状态解释、失败恢复、键盘操作及窗口缩放。隔离服务和程序检查通过不能代替这一阶段。

私有逐证据诊断分别保存为本次 run 目录内的 `diagnosis-qa-failures-v2.json`、`diagnosis-workflows-v2.json`、`diagnosis-evidence-routing-v2.json`；其中的原始业务内容不复制到公开文档。以上方案遵循[工程控制论指导原则](../../architecture/engineering-cybernetics-guiding-principles.md)与项目 `skills/agent-evolution/SKILL.md` 的观察、有限候选、匹配评估和可回退要求。

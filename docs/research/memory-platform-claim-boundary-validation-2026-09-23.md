# 平台回答证据主张边界验收

## 问题与实现

上一阶段已能查询历史失败 run 之后的运行，却仍见模型把四天前更新的 `loopStates.currentPhase=error` 说成此刻执行器仍阻塞。短记录原先直接返回字段，未明确区分“最后持久化”与“实时运行态”；预取说明也容易让模型拿到首轮证据后直接给出推测。

现在 `loopStates` 的短发现和精确读取均附 `temporalScope`：最后持久化时间、`currentRuntimeVerified:false`，以及 `updatedAt` 不是有效性区间。平台召回进一步生成 `claimBoundary`，将后续运行限定为读取时间/所有者可见范围内的观测，实时执行态标为未观测，修复标为未证实，列出 `present_unread` 字段，并说明 `allow` 只证明权限、不证明动作执行或外部状态改变。Jev 预取及普通平台提示均使用该边界；`recordRead.source` 的工具模式限制为固定发布来源名，避免把 `runs` 当成可读源。所有数据仍来自现有权限查询，没有模型写入记忆或自动执行动作。

离线审计只对明显的肯定/概率性实时状态句子产生 `claimRisks` 复核提示。问题标题、否定表达和“最后持久化为 error、实时态未知”不应误报；该正则检测不是语义判定器，`claimRisks:[]` 也不是答案正确证明。用户仍可在原始工具轨迹和验收文件中核对并纠正。

`.runtime/evals/memory-access/2026-09-23T09-20-56-811Z/`：模型正确解释了 `loopStates` 仅是最后持久化状态，但自动时间线的自然问法识别漏掉“失败后/修复”，于是误报后续运行证据缺失。扩展意图匹配后，`.runtime/evals/memory-access/2026-09-23T09-22-22-044Z/` 读到空的后续时间线，回答区分修复未证实与实时态未知；模型先猜 `recordRead.source=runs` 产生一次可见失败，随后纠正。加来源枚举后，`.runtime/evals/memory-access/2026-09-23T09-24-50-705Z/` 零工具错误，但答案仍写“执行器很可能非活跃或等待干预”，这条推断没有实时来源。

## 边界

结构化结论与提示降低了此样本的越界推断，但不能保证任意问题的语义正确；系统尚未拥有实时执行器观测，也没有验证未读字段值、外部动作结果或所有可能的修复来源。以后若接入实时心跳，必须作为单独来源标明观测时间和可靠性，不能用旧 `loopStates` 冒充。

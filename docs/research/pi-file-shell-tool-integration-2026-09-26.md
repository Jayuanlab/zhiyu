# Pi file and shell tools for Zhiyu workshops (2026-09-26)

## Finding

Pi itself supports reading and writing files and running commands. The official **coding-agent** application enables `read`, `bash`, `edit`, and `write` by default. The lower-level **agent-core** accepts only tools supplied by its host. Zhiyu embeds `@earendil-works/pi-agent-core@0.85.1`, not `@earendil-works/pi-coding-agent`; its workshop Pi adapter supplies `options.tools ?? []`. Consequently, the current workshop's missing file/shell capability is an integration and policy choice, not a Pi model limitation. Sources: [Pi coding-agent README at the installed-version pin](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/README.md), [Pi agent-core tools documentation at the installed-version pin](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/agent/README.md#tools), local `packages/ai/src/agent/runtime/pi-agent-adapter.ts`, `packages/ai/package.json`, `apps/web/package.json`.

## Official integration paths

1. **Keep agent-core and provide `AgentTool`s.** The first-party agent-core documentation defines `AgentTool` with a name, description, TypeBox parameters, and `execute(toolCallId, params, signal, onUpdate)`; the host places instances in the agent state. Pi emits tool-start, update, and end events, and tool errors should be thrown. This fits Zhiyu's existing `PiAgentRuntimeAdapterOptions.tools` seam and its audited domain-tool adapter. [Agent-core README: Tools](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/agent/README.md#tools).
2. **Use the coding-agent tool factories.** The first-party package exports `createReadTool(cwd)`, `createBashTool(cwd)`, `createEditTool(cwd)`, `createWriteTool(cwd)`, and `createCodingTools(cwd)` returning the four tools. This would add a new dependency to Zhiyu; the package must be integrated with Zhiyu's permission and audit layers rather than assumed to be available merely because agent-core is installed. [First-party tool exports](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/index.ts), [read factory](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/read.ts), [bash factory](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/bash.ts).
3. **Use a full coding-agent SDK session if its lifecycle is wanted.** `createAgentSession({ cwd, tools: ["read", "bash", "edit", "write"] })` selects built-ins and binds their paths to the supplied working directory. The SDK also supports `excludeTools` and `customTools`. This is a larger runtime replacement than adding tools to Zhiyu's existing agent-core adapter. [Official SDK guide](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/docs/sdk.md), [checked tools example](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/examples/sdk/05-tools.ts).

## Security and lifecycle facts

- The official bash tool accepts a `spawnHook` that can change command, cwd, and environment, and `operations` that can replace local execution. These are extension points, not a complete sandbox by themselves. A real isolation boundary must come from the host's worker/container, filesystem mount, credentials, and OS permissions. [Bash tool source](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/bash.ts).
- Coding-agent extensions can block or mutate tool calls, but run with the Pi process's OS permissions. That extension mechanism belongs to the coding-agent runtime; Zhiyu's current direct agent-core embedding should enforce its policy in host tool wrappers or agent-core preflight hooks. [Official extensions guide](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/docs/extensions.md), [agent-core preflight description](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/agent/README.md).
- `cwd` is a working directory and path-resolution parameter, not an authorization boundary. Do not rely on it alone to keep a file or shell tool inside a dataset directory. This is an engineering inference from the factories' path and spawn APIs, not a Pi guarantee. [SDK cwd description](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/docs/sdk.md), [bash tool source](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/bash.ts).

## Zhiyu-specific integration point

`createWorkshopPiTools()` currently classifies `Read`, `Edit`, `Write`, and `Bash` as built-ins and filters them from the Pi domain-tool request. It registers selected domain tools, Skill, and memory access only; `resolveWorkshopPiAllowedTools()` applies the workshop allow/deny policy to registered names. The workshop executor passes only that list to the Pi runtime. The separate grey-readiness code ignores host/skill names such as `bash`, `read`, `write`, and `xlsx` when judging Pi eligibility, which does **not** make them executable. Local sources: `apps/web/lib/workshops/pi-domain-tools.ts`, `apps/web/lib/workshops/tool-access.ts`, `apps/web/lib/workshops/pi-runtime-readiness.ts`, `apps/web/lib/workshops/executor.ts`, `packages/ai/src/agent/runtime/pi-agent-adapter.ts`.

To match Claude's practical read → generate script → execute → inspect loop, register audited Pi file/shell tools at this seam, extend the allow/deny and approval policy for those names, and expose execution results in workshop events. For a data-cleaning worker, mount or copy the immutable input into a per-run workspace, confine outputs there, prevent credentials and unrelated paths from being reachable, limit process time/resources, and record source version, generated code, execution result, and validation. The pinned source also exposes a PowerShell tool factory, so a Windows integration can evaluate that shell path rather than assuming Unix Bash. The selected shell and its behavior still need a local Windows smoke test. [Pinned tool exports](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/tools/index.ts).

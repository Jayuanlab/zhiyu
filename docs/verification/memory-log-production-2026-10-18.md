# LOG 保存修复与同车间连续生产验证

2026-10-18，修复后的正式生产版本在同一车间、同一手动 Loop 连续完成 FIX1、FIX2 两轮真实模型任务。两轮均保存了新的、绑定真实来源的 LOG，召回了当前主人纠错；第二轮继承了第一轮的确切检查点、根及原始有效期。主任务、召回规划器、质量评估及运行清理均完整结束。

**本次所要求的保存、召回和跨轮继承已获得两轮生产证据；预先约定的严格总验收仍为失败。** 唯一未满足项是“至少一个成功轮次自主展开 typed owner 原始证据”。两轮均使用了完整召回的当前记忆，但没有调用该展开工具，不能把召回或搜索等同于原始证据展开。原 LOG1 失败、旧阶段失败和严格判决全部保留。

可复核的脱敏汇总见 [JSON 证据](./evidence/memory-log-production-2026-10-18.json)，变更和预算边界见[初始方案](../plans/memory-log-production-2026-10-18.md)与[剩余两轮补丁方案](../plans/memory-log-postfix-2026-10-18.md)。更早的 V1 未保存 LOG 等结果保留在[上一阶段报告](./memory-production-stability-2026-10-18.md)。

FIX1 约 109 秒、6 次工具调用；FIX2 约 114 秒、7 次工具调用。两轮均在每轮 18 次物理请求、14 次工具调用、420 秒和一次任务尝试的边界内，没有自动重跑任务。

FIX1 的 8 次主链路物理请求对应 7 次逻辑主调用：其中一次不透明的空响应错误触发了同请求的一次有界传输恢复，恢复后得到完整终态，没有重放整项任务或重复执行领域动作。FIX2 没有传输恢复。两轮均未实际触发宿主报告纠正或上下文压缩，因此提高后的纠正输出额度有程序覆盖，但尚无本次生产触发证据。

## 为什么这次能证明记忆链路

**保存可核对。** 两轮都有模型主动提交、宿主实际接受的 LOG v1；笔记绑定本轮真实观测来源。交付检查读取已经提交的工作记忆快照和同轮持久事件，在候选最终结果和运行结束后分别核对，均通过。最终报告文本不能替代这份证明。两轮在首次尝试使用未知来源标识时各有一次拒绝，随后读取实际来源目录并自行纠正，再成功保存；拒绝事件仍保留。

**召回使用了当前纠错。** 两轮每份实际普通主请求都包含完整的 323 字符当前记忆、真实置信度 25、active 状态和匹配版本，并包含当前结构化保存合同。没有提高置信度、缩写纠错或把已被替换的旧建议恢复成现行规则。

**跨轮继承没有偷偷续期。** FIX1 面对最近失败的 LOG1，明确记录跳过失败检查点，也没有退回更早的祖先。FIX2 输入中的来源运行、检查点、根、原始创建时间和有效期与 FIX1 完全一致；继承来源的有效期仍是北京时间 2026-10-25 18:04:54。FIX2 随后凭新的来源观测保存自己的 LOG，创建新的根；新笔记的有效期不算旧根续期。

**纠错优先于历史笔记。** FIX2 继承时，历史事实、假设和行动建议因当前纠错被抑制，保留一个真实未决问题；历史来源引用没有冒充本轮可用的 evidenceId。重新阅读来源后才建立本轮笔记。历史正文保留在审计中，继承只传递受控状态。

**辅助链路完整结束。** 两轮的召回规划器和质量评估均实际调用模型、取得完整响应；质量评估使用 LLM 模式并通过，没有把规则降级标成模型成功。两轮主链路 SDK 用量回执完整，货币费用未计算。

## 修复了哪些真实问题

1. **把保存证明与历史传输分开检查。** LOG1 笔记状态仅 1,074 字符，但多个位置重复展开来源信息，未应用纠错的展开形式超过 8,000 字符，错误触发交付拒绝。现在先严格核对持久 LOG、来源、hash、窗口、版本、作用域和时效，再独立检查真正用于继承的纠错后表示。原 8,000 字符传输上限仍有效，没有截断来源或放宽越界条件。
2. **使用当前行的保存合同。** 旧的持久 `loopSpec` 曾遮蔽刚启用的合同字段。现在该字段由当前配置决定；已撤销的合同也不能从旧状态复活，其余历史配置语义不变。LOG1 当时已有纯文本约束且宿主门禁确实执行，不能说整个合同完全没有生效。
3. **让输出中断有有限恢复空间。** LOG1 的四次有界报告转发最终遇到长度终态；它消耗 17 次请求、约 257 秒，并未超过整轮请求或时间上限。修复保留一次纠正、最多四次转发及整轮期限，将纠正总输出额度调整为 16,384 token，并要求紧凑报告；最多一次、2,048 token 的压缩仍共用这笔额度，不续期。
4. **明确辅助质量 JSON 的合法格式。** LOG1 返回完整 JSON，但严重性字段不符合枚举，因此降级。现在提示中明确字段类型和枚举；解析器仍严格拒绝非法值，没有强制映射为成功或追加评估重试。旧返回的具体非法值没有完整记录，不能推测是哪一个值。

## 已装载与程序验证

新生产候选 review93 完成正式构建、构建前后 TypeScript 检查，并装载到本机生产 Web 和长期 worker。最终只读观测核对了 HTTP 身份、实际提供的构建资源字节、457 份来源文件、进程父子关系、worker 心跳和 FIX2 持久状态，全部一致；该观测没有新建任务或进行模型探测。

worker 仅启用 `loop-execution`，限定同一个授权车间，排除其余九个模块。Loop 为手动触发；权限、denied 优先和审核边界未扩大。当前生产保持在线。

本次运行时相关八组针对性测试通过 243/243，新增阶段审计工具测试通过 72/72；两次成功生产任务及只读装载检查是独立证据。程序检查覆盖快照真实提交、旧配置冲突、纠错后的传输边界、过大未决问题、错误来源、非法质量枚举、租约和期限等失败分支。

本授权累计实际运行三次任务、38 次生产物理模型请求，其中最初失败 LOG1 占 17 次，两轮补丁复验占 21 次。连同更早阶段累计七次任务、67 次生产请求；五次更早的认证诊断单列。未重置预算，也未启动原 LOG2、LOG3 或在严格总验收失败后追加任务来凑通过。

## 桌面可用性与剩余项

桌面已定位至 FIX2 的完整工作记录，可以查看 LOG v1、来源数、继承来源、原有效期、当前纠错优先提示及最终报告。页面中的一次未知来源拒绝也可见。保留以下 P2 体验问题，未标记完成：

- 未指定运行的默认面板没有自动选择最新 Loop 记录；从“查看完整工作记录”再“定位此运行”可以查看。
- 工作复盘卡片的目标与结构化状态映射不完整，仍显示“处理需求待核实”等提示，与已完成的后端终态不一致。
- 继承详情直接展示内部标识和英文约束，阅读成本偏高。

这些问题列入桌面记录展示的后续改进，不用改文案掩盖运行证据。生产运行时在验收前已冻结，本阶段没有为了界面调整再次换包或重跑模型。

严格总验收的唯一剩余项仍是成功任务自主展开 typed owner 原始证据。失败的 LOG1 虽曾展开过，也不能替成功轮次满足这一要求。本报告确认的是同一受控车间的真实记忆机制，不证明自然业务任务质量提高、费用下降或所有未来任务都能稳定成功。
